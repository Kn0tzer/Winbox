## The fault, in plain terms

The test program calls a helper that is supposed to throw a real C++
`bad_function_call` exception. Instead the guest program crashed reading
memory it should never have touched, and printed no result at all.

What happened, step by step:

1. The helper lives in `msvcp140.dll`. The FD-167 patch gave that DLL the
   tables describing the exception types, but never switched them on: the
   three start-up calls that fill those tables were missing from
   `init_exception()` in `dlls/msvcp90/exception.c`.
2. On 64-bit only, those tables start out filled with the placeholder value
   `0xDEADBEEF`. The test's exception handler walks the tables, so it read
   the placeholder as an address: fault address `0x33f8ebef3` is exactly the
   DLL's base (`0x360e10000`, as the test itself printed) plus the
   sign-extended placeholder `0xDEADBEEF` plus 4. The guest died with
   `BW64-FAIL guest-memfault pid=48 addr=0x33f8ebef3 rip=0x14000166d`,
   exit status 3221225477, no `RESULT` line.
3. 32-bit was never affected: its tables hold real pointers and need no
   start-up calls. The batch-9 gate log and its re-run reproduced the
   64-bit crash identically (same fault address, same exit status).

## Fix 1 — switch the exception tables on (the real fix)

`tools/buildWine/patches/wine8-fd167-contracts.patch`: new hunk in
`init_exception()` adding `init_bad_function_call_rtti(base)`,
`init_system_error_cxx(base)` and `init_bad_function_call_cxx(base)` in
the existing `_MSVCP_VER > 90` blocks. Verified the patch applies cleanly
to the Wine 8.0 tree and that the rebuilt `init_exception` stores the
table addresses (object-level check of `exception.o`).

## Fix 2 — one wrong number in the test itself

With Fix 1 in place the test ran to completion: 14 of 15 checks passed.
The one failure was `SetupDiGetDeviceInterfaceAlias A->C absent`:
the test expected error code `0xE00002C7`, the DLL returned `0xE0000225`.

The DLL was right and the test was wrong:

- Wine 8.0's own `include/setupapi.h` defines
  `ERROR_NO_SUCH_DEVICE_INTERFACE` as
  `(APPLICATION_ERROR_MASK|ERROR_SEVERITY_ERROR|0x225)` = `0xE0000225`.
- Wine master (fetched 2026-11-06 from gitlab.winehq.org) defines the same
  `0x225`; no `0x2C7` anywhere in its `setupapi.h`.
- mingw-w64's current headers define the same `0x225`.
- The `0xE00002C7` literal appeared nowhere else in the tree and was never
  validated: the 32-bit fixture has no alias checks at all, and the 32-bit
  `setupapi.dll` ships `SetupDiGetDeviceInterfaceAlias` as an
  unimplemented stub, so no earlier run ever proved `0x2C7`.

`tools/guest-fixtures/fd167-contracts64.c:257`: expectation corrected to
`0xE0000225` (comment cites the `setupapi.h` definition). The DLL was not
changed for this check; its `SetLastError(ERROR_NO_SUCH_DEVICE_INTERFACE)`
is the only use of that constant in the Wine 8.0 tree.
