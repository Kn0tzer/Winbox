# FD-28 — the Vulkan host generator learns the hand-written vk_host.cpp implementations

Branch `lane-vkhost-gen`, base integ `faf95d26c`.
Fix commit `26a90c5b6`. Register: FD-28 closed as CL-137
(provisional; the number settles at the next composition).

## The defect

`source/vulkan/vk_host.cpp` opens with "DON'T MODIFY, this is
autogenerated", but it carried hand-written implementations its
generator (`tools/vulkan/gen`, a Java program run as
`boxedwine.org.Main` from the repo root over
`lib/mesa/vkRegistry/vk.xml`) did not emit. Anyone regenerating
the Vulkan host bridge would silently revert them. FD-28's terms:
either the generator learns those implementations, or the file
stops presenting itself as generated. This lane does the first.

## Baseline measurement (base tip, unmodified generator)

Regenerating on `faf95d26c` changed exactly one file:
`source/vulkan/vk_host.cpp`, 66 insertions / 69 deletions —
identical to the figure the tooling-honesty lane measured on
2026-10-30, so the drift was stable, not growing. Every other
output (`vk_host.h`, `vk_host_marshal.cpp`, `vk_host_marshal.h`,
`tools/vulkan/vk.c`, `tools/vulkan/vkdef.h`) already regenerated
byte-identically. The full baseline diff is preserved at
`test-results/fd28/baseline-regen.diff`. The divergence, by kind:

- initVulkan error propagation: the shipped prologue declares
  `bool initVulkan()` and the two generated functions that call
  it guard on failure and return
  `VK_ERROR_INITIALIZATION_FAILED`; the generator emitted a
  `void` declaration and bare calls.
- Map-failure handling: in `vk_MapMemory`, `vk_MapMemory2` and
  `vk_MapMemory2KHR`, a zero guest address from `mapVkMemory`
  becomes `VK_ERROR_MEMORY_MAP_FAILED` (and `vk_MapMemory` also
  unmaps on the host); the generator wrote the result out
  unconditionally.
- Push-descriptor-template support:
  `vkCmdPushDescriptorSetWithTemplate{,KHR}` size the template
  data with `calculateUpdateDescriptorSetWithTemplateDataSize`,
  lock the guest data read-only, forward it, and unlock; the
  generator emitted a `kpanic` "not implemented" stub with a
  null data pointer.
- Log-once graceful degrades for eight functions the emulator
  cannot honour with a host call: the five
  `vkGet*OpaqueCaptureDescriptorDataEXT` getters and
  `vkGetDescriptorSetHostMappingVALVE` answer
  `VK_ERROR_FEATURE_NOT_PRESENT` / a null out-pointer,
  `vkGetMemoryHostPointerPropertiesEXT` answers
  `VK_ERROR_INVALID_EXTERNAL_HANDLE`, and `vkCmdSetCheckpointNV`
  is a no-op — each logging once. The generator emitted
  `kpanic` stubs that still called the host with null arguments.
- Unknown-pNext handling: `vulkanGetNextPtr`,
  `vulkanDeleteNextPtr` and `vulkanWriteNextPtr` log an unknown
  sType once and skip the node (for GetNextPtr, preserving the
  rest of the chain); the generator emitted
  `kpanic_fmt("... not implemented for %d")`.

These shipped shapes are pinned by the JS unit test
`web/tests/suite/unit/vk-panic-stubs.test.mjs`, which reads the
shipped file — so the fix had to reproduce them exactly, not
approximately.

## The fix (commit `26a90c5b6`, generator sources only)

Following the generator's own established pattern of name-keyed
special cases (the `vkMapMemory` marshal routing, the
debug-callback handling in `VkHost.hostCall`, and the FD-27-era
log-once emission added to `VkHostMarshalType` by the
tooling-honesty lane):

- `writers/VkHost.java`: the prologue declares `bool
  initVulkan()`; the per-function preamble becomes the guarded
  form. A new `writeCustomFunctionBody` emits the eight degrade
  bodies verbatim. The three unknown-sType defaults emit the
  log-once-and-skip shapes — this also discharges the
  next-pointer-writer part of FD-27 (its two union types in the
  marshal generator remain open under FD-27).
- `marshal/VkHostMarshalMapMemory.java` and
  `VkHostMarshalMapMemory2.java`: `after()` emits the shipped
  map-failure handling.
- New `marshal/VkCmdPushDescriptorSetWithTemplateMarshal.java`,
  routed from `VkHostMarshalType` for the two
  `vkCmdPushDescriptorSetWithTemplate{,KHR}` `pData` parameters,
  mirroring what `VkUpdateDescriptorSetWithTemplateMarshal`
  already did for the non-Cmd variants (with the Cmd variants'
  null-data guard).

No shipped file changes: the commit touches only the five
generator sources (one new).

## Finding filed from this lane: FD-194 (queue mount race)

The checking queue's executor mounts one shared source tree
(`winbox-project/checks/src`), and every `submit-check` run
re-prepares that mount to its own lane's commit before
creating its pipeline. When submissions overlap, every
still-queued pipeline mounts whichever commit was prepared
last. During this lane's run the parallel-lane wave submitted
heavily: pipelines 18 (this lane), 19, 20 and 21 were created
for four different commits and all four mounted a fifth
lane's commit (`81bd25c49`, lane-x11-getramptr-audit) and
failed at verify-source with no check results; only
pipeline 17, whose submission did not overlap, verified.
The failure is fail-closed — no lane received a wrong pass —
but each new submission can void runs already queued, so the
queue is unusable under concurrent submission until
submissions serialize (a lock in `submit-check`) or each
pipeline gets its own mount. Filed on the register as FD-194
(lane-local number; FD-193 is claimed by three sibling
branches). Evidence: `checks/evidence/pipeline-18/`
through `pipeline-21/` on the box.

## Environment note

The worktree was created with `git worktree add` at the base
tip, but `winbox-wt-prep.sh` aborted before linking: the shared
store's `wine64.zip`, `wine32.zip` and `prefix32.zip` were
replaced (2026-11-07 03:27 UTC, with the store's `SHA256SUMS`
updated to match, so the store is internally consistent) and no
committed manifest — the base tip's included — matches the new
zips. That is another lane's in-flight payload work, not this
lane's to reconcile; this lane needed no payloads (the generator
runs on the JDK alone) and the checking queue prepares its own
pristine checkout, so the lane proceeded unprepared rather than
disturb the store. If the store refresh is yours, the prep
script will keep refusing fresh worktrees until a manifest is
re-pinned to the new zips.
