# FD-40 fix record — the unsigned win32u rebuild (2026-10-31)

Branch `lane-fd40-fix`. Supersedes the mechanism in
`docs/reports/fd40-boot-smoke-characterization-20261031.md` (that
record's *observations* were accurate; its mechanism was wrong, in a
way this record corrects with the evidence that settled it).

## What the failure actually was

The boot smoke test waits for four milestones; the fourth,
`create_winstation`, never happened — in any process, in any run, on
any build carrying the current payloads. Everything else in the
session worked, which is what made it elusive.

Two corrections to the characterization record first:

- The exact-30 s `DBWIN_BUFFER` reopens it convicted are **not a
  parked boot thread**. They are the session anchor program's
  designed heartbeat: `tools/rootfs64/gltest/deskpin.c` sleeps 30 s
  and calls `OutputDebugStringA` in a loop, forever. Wine 8.0's
  `OutputDebugStringA` (`dlls/kernelbase/debug.c`) is single-attempt
  — it opens `DBWIN_BUFFER` once per call and returns silently when
  no listener exists. The heartbeat lines dominate the late log
  simply because every other process has exited and deskpin is the
  only one left talking.
- The boot thread was never waiting on debug output. Session
  initialization itself never ran: no process on a failing build
  performs any of the server-visible steps of user32 initialization
  (no Fonts-key enumeration, no `get_process_winstation`, no
  `create_winstation`), even though user32.dll loads and its attach
  completes.

## The convicted mechanism

user32's per-process initialization calls
`NtUserInitializeClientPfnArrays` in win32u.dll — a syscall stub
(number 0x10b3) whose real body lives in the unix-side `win32u.so`
and does the font load, the window-station creation, and the system
parameter setup. Whether those syscalls are ever dispatched depends
on the loader treating win32u.dll as a Wine **builtin**: the
wineserver and the unix loader key that treatment off a 32-byte
signature, the literal text `Wine builtin DLL`, that winebuild
stamps over the DOS stub at file offset 64
(`make_builtin_files`, tools/winebuild/spec32.c).

The staged win32u.dll is a from-source rebuild (the wine8 backport
set). The backport build's mingw cross tree links plain PE files and
nobody stamped them, so the rebuilt DLL has a standard DOS stub
where the signature belongs. Consequences, each verified:

- Byte level: stock DLL carries the signature at offset 64; the
  rebuild (sha256 a8ca5fbb…, 354,218 bytes) does not. The two files'
  syscall stubs (276), syscall-number assignments (4096–4371), and
  .rodata are identical — the stub layer is innocent.
- Server level: the wineserver's `get_mapping_info` reports
  `image_flags=0x44` for the stock DLL (WineBuiltin 0x40 |
  dynamically relocated) and `0x04` for the rebuild — the builtin
  bit is exactly what is missing.
- Behaviour level, three-arm A/B on identical trees (instrumented
  boot through the project's probe slot; milestones are guest-log
  timestamps): unstamped rebuild — execve 27.4 s, user32 114.5 s,
  **no winstation, ever**; stock Debian DLL — winstation **106.4 s**;
  the same rebuild with only the signature stamped — winstation
  **102.0 s**. Evidence: `test-results/fd40fix-diag/diag1/`
  (unstamped), `.../ab-stock/`, `.../ab-stamped/` in this lane's
  tree.

Without the builtin registration, win32u syscalls from PE callers
never reach their implementations and fail silently, so user32
initialization is a no-op in every process. (The session still
*looked* alive — the emulator's own console and window layers do
not depend on that path — which is why only this test, which
watches for the window station itself, caught it.)

All five rebuilt backport DLLs lack the signature. Only win32u is a
syscall DLL, and only it shows a symptom; the other four
(user32/kernelbase/kernel32/iphlpapi) carry real PE code and load
fine as native DLLs.

## The fix

- `tools/rootfs64/build-wine8-backports.sh` now stamps every DLL it
  rebuilds with the builtin signature, byte-for-byte the way
  winebuild's `make_builtin_files` does (assert MZ, assert
  `e_lfanew >= 96`, write the 32-byte signature at offset 64), with
  a comment naming FD-40 so the step is never dropped as noise.
- The shipped `win32u.dll` in `tools/rootfs64/wine8-backports-x86_64/`
  was stamped in place: sha256
  `a8ca5fbb…` → `49b874381063acf28652bee5a4c281b21582830b50190d9c2c9875fd5deff708`,
  size unchanged (354,218). Only header bytes 64–95 changed; every
  byte of code is the pipeline's own rebuild.
- Re-pinned through the normal flow: the completeness checker's
  `WINE8_BACKPORT_PINS`, the backports README table, the rebuilt
  `wine64.zip` member (zip sha256
  `e777d0522e96215006281824e98858be31c7642058ff0551e3d7aaee16b5f5c4`),
  `tools/browser/runtime-assets.json`, and the regenerated runtime
  artifact manifest. `check_runtime_completeness.py`: **0 failures,
  1 skip**.
- The other four DLLs are stamped by the script on their next
  rebuild (their pins update at that point, per the script's
  existing re-pin instruction). They were deliberately not re-staged
  in this lane: no symptom, and the change surface stays on the
  convicted file.

## Proof

- **A — the boot smoke test, through the project's own suite path:**
  `BW_TEST_DIST=<this tree>/dist node web/tests/suite/runner.mjs
  --filter=boot64-smoke` — **passed three times in a row (89 s,
  82 s, 91 s)**. Before the fix the same test never completed (the
  characterization record: its 240 s watch expires, 5/5).
  Instrumented-boot evidence shape restored: `create_winstation`
  reached (winstation milestone 102.0 s on the stamped build).
- **B — the debug-output channel still works for its real
  purpose:** new guest fixture `tools/guest-fixtures/dbwin-echo.c`
  and suite test `web/tests/suite/browser/dbwin-echo.test.mjs`. The
  fixture's listener half creates the DBWIN monitor objects
  (`DBWIN_BUFFER` section, `DBWIN_BUFFER_READY`/`DBWIN_DATA_READY`
  events, `DBWinMutex`), spawns its sender half, and the sender's
  `OutputDebugStringA` token arrives in the shared buffer verbatim
  (`RESULT 0`). Suite: **passed (93 s)**. When nobody listens,
  senders still abandon the send silently, exactly as the protocol
  intends — the heartbeat behaviour that started this investigation
  is unchanged and correct.

## Found on the way (registered as FD-43)

The FD-01 desktop-wait patch edits `get_desktop_window` and
`load_desktop_driver` — functions that exist only in the unix-side
`win32u.so`, in neither PE win32u.dll (stock or rebuilt: no strings,
no 300 s constant). The shipped `win32u.so` is byte-identical to
the container staging image's (`5dac5821…`), and its single
`NtUserWaitForInputIdle` call site passes the stock 10 s timeout —
so the patch's code is present in **no shipped binary**, before or
after this fix. FD-01's live measurements (0/4 → 6/6 first-attempt
starts) stand as measured, but the improvement is not attributable
to the patch as shipped. Because this fix restores win32u's builtin
treatment (behaviour closer to the pre-FD-01 stock DLL), FD-01's
live first-visit rate should be re-measured on the merged build
before the restart stopgap's retirement is treated as settled.
Details in register entry FD-43.
