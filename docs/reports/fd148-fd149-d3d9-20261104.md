## FD-148 — the D3D9 clear never reaches the compositor with its final red

**Reproduction (base, wasm 05298a62).** `d3d9-comprehensive` FAIL,
219,863 ms: "x64 DXVK clear must reach the browser compositor with
its final red color — expected > 100000, got: 4". All three guest
stages (clear9, texquad9, scene9) complete; CAPTURE_READY appears;
both swapchains sit at the correct 632x453. (The FD-125 settlement
run's intermittent 632x1 swapchain-extent collapse was NOT
reproduced on this base; see Notes.)

**Localisation.** The suite's per-pass readback diagnostic
(`?bwPassReadback=1`) showed submission 59's render target (the
clear's image, 640x480) reading back constant [232,40,100,255] —
the clear lands exactly. Submission 60 (the present blit) executed
one draw sampling that same texture, yet the swapchain target
(632x453) read back ~black (1 non-black pixel). Temporary gated
instrumentation (reverted after use) proved the blit bind group
sampled texture id=1, the very texture the clear wrote
(`viaAlias=true`) — the data path was intact; the sampling was
wrong. The guest shaders, disassembled: the blit fragment shader
computes `coord = src_offset + src_extent * i_coord` (texel space,
0..640 x 0..480) and samples with OpImageSampleExplicitLod; the
vertex shader is a standard fullscreen triangle, and its naga WGSL
is correct.

**Cause.** DXVK's swapchain blitter
(`tools/dxvk/src/src/dxvk/dxvk_swapchain_blitter.cpp`, used by
D3D9's presenter) creates its present sampler with
`usePixelCoord = VK_TRUE` — Vulkan's `unnormalizedCoordinates` —
with CLAMP_TO_BORDER addressing and a transparent-black border: it
samples in texel space by design. The emulator's bridge marshalled
the flag in the guest struct (`vk_host_marshal.cpp`) but its
Sampler record dropped it; `web/vk-protocol.mjs` and the page tier
had no unnormalised handling anywhere. WebGPU samplers are always
normalised, so texel-space coordinates sampled far outside [0,1],
and the page tier's CLAMP_TO_BORDER emulation masked everything to
the border colour except a sub-texel corner — exactly the observed
signature (redDominant 4, not 0). D3D10/11/12 present their
swapchain images directly and never use this blitter, which is why
only D3D9 hit it. DXVK's HUD renderer uses usePixelCoord samplers
too and is covered by the same fix.

**Fix (`5ac7f7431`).** The flag now travels end to end. The bridge
stores `Sampler.unnorm` from both vkCreateSampler ABIs and appends
it to the SAMPLER record after the SAM1 tail
(`writeSamplerRecordPayload`); `web/vk-protocol.mjs` decodes it
only when bytes remain (old records default false — the reader's
`done()` throws on trailing bytes, so both ends ship together).
`web/wgsl-utils.mjs` gains the unnorm plan machinery
(`unnormPlanForDecls` / `unnormPlanSignature` /
`rewriteUnnormalizedSamplersWGSL`), mirroring the border-plan
machinery: sample-call coordinates (and textureSampleGrad
gradients) are divided by `textureDimensions`, level-aware for the
*Level call family; cube/gather/load calls are untouched.
`web/vkwebgpu.mjs` adds a per-draw pipeline variant in
getPipelineFor, gated on the frame actually binding an
unnormalised sampler and keyed on the plan signature, applied
BEFORE the border rewrite so the border plan's [0,1] tests see
normalised coordinates. The composition was self-tested in Node
against the real blitter WGSL before the build.

**Proof.** Base FAIL got 4 (twice: `run-base-comp.log`,
`run-base-diag.log`) → fixed PASS, all stages RESULT 0,
redDominant 722,880 (`run-fix1-comp.log`,
`fixed-clear-pixels.json`); re-run PASS on the final tree
(`run-fix2-comp.log`, 173,932 ms). Regression controls on the
fixed build all PASS: d3d11-triangle, d3d11-comprehensive,
d3d10-comprehensive, d3d12-comprehensive (`run-fix1-controls.log`).
New unit suite `web/tests/suite/unit/vk-unnorm-emulation.test.mjs`
7/7; `vulkan-sampler.test.mjs` updated to pin the 72-byte record
and the `unnorm: true` decode (`82e3ebb51`).

**Fallout.** The fix's insertions shifted line numbers in
`web/vkwebgpu.mjs` (+25..+40, growing per insertion region) and
`source/vulkan/vk64bridge.cpp` (+8), rotting 41 mechanically

`vk-register-citations` caught it (it passes on the base and

UNCHECKABLE / 7 EXEMPT.

## FD-149 — the 32-bit D3D9 capture never becomes ready

**Filing's evidence.** The 32-bit session boots; clear9's process
prints `err:vulkan:vulkan_init_once Wine was built without Vulkan
support.` and `Failed to load Wine graphics driver supporting
Vulkan.` (x2); DXVK aborts with `Required Vulkan extension
VK_KHR_surface not supported`; CAPTURE_READY never appears in the
300 s wait. The x64 console has zero such lines.

**Cause (proven from the payloads and the build scripts).** The
shipped 32-bit `win32u.so` is the FD-02 backport (sha256
`b2d9d135...`, committed at `tools/rootfs32/wine10-backports-i386/`;
both zip placements carry the same bytes). The stub string "built
without Vulkan" exists ONLY in that 32-bit module — the 64-bit
module is FD-65's Vulkan-capable rebuild, and the rest of the
32-bit tree is stock and Vulkan-capable (winex11.so carries
`X11DRV_vulkan_surface_create`; winevulkan is present).
`tools/rootfs32/build-wine10-win32u.sh` configured its i686 tree
with `--without-vulkan` in the WITHOUTS list: its private sysroot
carried only the freetype/fontconfig deb closure, so the configure
could not have found Vulkan anyway, and its fail-closed markers
checked only the font defines (HAVE_FREETYPE, SONAME_LIBFREETYPE,
SONAME_LIBFONTCONFIG) — nothing noticed the FD-02 rebuild silently
losing the stock WineHQ module's Vulkan driver entry. win32u is
where that entry lives (`__wine_get_vulkan_driver`), so every
32-bit session failed its graphics-driver load before DXVK could
ask for a surface. The cause is the project's own build pipeline.

**Fix (`6e3dba081`).** In `build-wine10-win32u.sh`: `--without-vulkan`
removed from the i686 WITHOUTS (the native tools tree keeps it —
tools only); the sysroot deb set gains bookworm i386
`libvulkan-dev_1.3.239.0-1` (sha256 `1488026b...`) and
`libvulkan1_1.3.239.0-1` (sha256 `a0b91b40...`); the i686 configure
LDFLAGS gain the sysroot `-L` paths; `SONAME_LIBVULKAN` joins the
fail-closed markers; and a product check refuses a module carrying
the stub string. The rebuilt module: sha256
`9d538e799c0b88b2c7ee1e15b9d71a979414d65de878459470d6395c12542df8`,
1,502,028 bytes. Independently verified: stub string count 0;
`__wine_get_vulkan_driver` and `libvulkan.so.1` present; config.h
carries `#define SONAME_LIBVULKAN "libvulkan.so.1"`; DT_NEEDED
unchanged (ntdll.so, libm.so.6, libc.so.6 — Vulkan is dlopen'd);
maximum glibc symbol version GLIBC_2.35.

**Restage (the sanctioned path, no hand edits).**
`tools/rootfs32/regen-wine32-zip.sh`: member verification
"IDENTICAL member set, sizes and sha256, except the four win32u
backport members at the committed pin". New wine32.zip: 239,697,077
bytes, sha256 `cffa5e42a91478c561b64bbaaba93170c036263fa04d8ff450bb4fcff1901927`.
The retained archive was rebuilt deterministically (manifest member
order, zeroed tar metadata, FD-73 pattern) as
`browser-runtime-20261104.tar` (514,457,600 bytes, sha256
`3c80c8a14e77e88a93fe5b9ce80d50077a457370aa7546070a211d95172062ba`),
placed at `/home/ubuntu/backups/winbox-runtime-assets-20261104/`,
and `tools/browser/runtime-assets.json` re-pinned to release
`runtime-assets-20261104`. `gen_runtime_manifest.py` regenerated
`docs/known-gaps/runtime-artifact-manifest.md`;
`check_runtime_completeness.py` passes with 0 failures;
`bootstrap.py --local` verifies the new archive (13 files); the
browser export rebuilt and verified (support archive pin
`c4dbe35986a5` unchanged). Pins updated in
`check_runtime_completeness.py` (WINE10_BACKPORT32_SHA),
`build-wine32-base.sh` (BACKPORT32_SHA), and the backports README.

**Proof.** Base FAIL (CAPTURE_READY never seen; stub lines in the
console) → fixed: **d3d9-32 PASS, 62,685 ms**; the presented clear
reads redDominant 722,880 — the identical count to the fixed x64
run; zero "built without Vulkan" lines and zero VK_KHR_surface
aborts in the console (`run-fix1-d3d9-32.log`, `fixed32/`).
d3d9-comprehensive re-run PASS on the same tree. The 32-bit
session boots through desktop initialisation and runs all three
staged programs, so the FD-02 desktop-wait fix the backport exists
for survived the rebuild.

  does not reach the suite console log in this pipeline;

  ReferenceError: `createVkRenderer2` is the v2 factory closure
