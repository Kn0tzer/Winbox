# Guest DNS resolution — end-to-end proof (FD-04 clause)

Date: 2026-11-07. Branch: `lane-dnsresolve` (off integration tip
`faf95d26c`). Code commit: `b3bc87931`.

## End state asked

A guest program can resolve a host name through the emulator's own
name-resolution interfaces and connect to the result — proven end
to end with a minimal test program. The shipped product's opt-in
networking default does not change; this proves capability only.

## What was proven

Suite test `web/tests/suite/browser/winsock-dns.test.mjs` (tag
`winsock-dns`) boots the branch build with the opt-in flags
`network=1&wisp=1` on x86 and on x86-64 and runs the minimal
Winsock fixture `tools/guest-fixtures/win32-dns.c`, which:

1. `getaddrinfo("example.com", "80")` — must return 0 and a
   dotted-quad IPv4 address;
2. connects to that address (non-blocking connect with a select
   deadline, the tree's established pattern) — must succeed;
3. sends an HTTP GET and reads the reply — must begin
   `HTTP/1.1 200`;
4. `getaddrinfo("bw64-nonexistent.invalid")` — must fail, or, if
   it ever resolved, its connect must fail. The fixture prints
   `BW_DNS done=1` only when the good path fully passed AND the
   bad name produced no working connection.

Result: **PASS** — runner output `PASS winsock-dns`,
`SUITE RESULT: 1 passed, 0 failed`, on the build of `faf95d26c`
(`test-results/suite-winsock-dns/BUILD_INFO.json`: wasm sha256
`92b36180…`, identical to the shipped batch-9 wasm — this lane's
changes are test-only).

Evidence, from the preserved
`test-results/suite-winsock-dns/console.log` (the x86 run's guest
output arrives through the guest console as a terminal escape
stream; shown ANSI-stripped, the same transform the harness
applies before matching):

- x86: `BW_DNS gai=0`, `addr=172.29.1.0`, `connect=0`,
  `http=1 bytes=928`, `bad_gai=11001`, `done=1`
- x86-64: `BW_DNS gai=0`, `addr=172.29.2.0`, `connect=0`,
  `http=1 bytes=928`, `bad_gai=11001`, `done=1`

`bad_gai=11001` is WSAHOST_NOT_FOUND: the unresolvable name
fails promptly with a resolution error — no hang, no timeout,
no false success.

## How resolution works on this path (as read from the tree)

- With `network=1&wisp=1`, `web/runtime.html` plants the guest
  `/etc/resolv.conf` (nameservers 1.1.1.1 and 8.8.8.8,
  `options use-vc`), so the guest resolver speaks TCP to
  port 53.
- `web/network.mjs` (`installWispSockets`) intercepts port-53
  streams in the Emscripten socket layer and answers A queries
  from its DNS map, handing out synthetic IPv4 addresses (the
  172.29.x.x values above). A connect to a synthetic address is
  translated back to the host name and carried over the wisp
  relay (`wss://kn0tzer.work.gd/wss/`), which resolves and
  connects for real. Relay policy: TCP 80/443/8080/8443,
  private/loopback destinations blocked.
- The native (non-browser) path is separate: the native
  rootfs `resolv.conf` points at 127.0.0.1 and the kernel
  answers loopback DNS queries itself
  (`source/kernel/knativesocket.cpp` `serveLoopbackDnsQuery`,
  answered from host `getaddrinfo`), covered natively by
  `source/test/process/testDnsService.cpp`. This lane's browser
  proof does not re-prove the native path; that native test
  is part of the light-check set the branch goes through in
  the checking queue (see the queue note in Process notes).

do not exist, the networking campaign remains parked by

in the kernel resolves names for the guest. That premise is
