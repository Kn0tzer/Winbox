# FD-131 — an empty path answers -ENOENT at the path calls generally

Lane `lane-fd131`, based on `lane-fd126` tip `20d2e8e01`.
Commits: tests `9946c1023`, fix `a8d43046c`, this
register/record commit. Closure CL-77 (provisional; this
lineage's entry numbers renumber at the batch-5 merge audit).

## The defect, by substance

An empty path given to a path system call resolved to the
directory node itself in the shared path resolver
(`Fs::getNodeFromLocalPath`): a full path of "" or "/" returns
the root node, and a relative empty path joins to the working
directory, whose walk returns the directory node — an empty
final path was never refused. Calls therefore answered as if
the directory had been named where the host answers -ENOENT:
`open("")` opened the directory, `stat("")` stat'ed it,
`mkdir("")` answered -EEXIST, `symlink("", name)` created a
link with an empty target. The FD-126 lane fixed the two
64-bit dispatcher sites it had measured (chmod, fchmodat;
CL-76) and filed the general case as FD-131.

## Host measurement (box kernel, aarch64)

Reference programs `hostref-fd131.c` / `hostref-fd131b.c`
(evidence in `test-results/fd131/`), using asm-generic/libc
syscall numbers. Every path-only call with "" answers
-ENOENT: open (including the O_CREAT form), stat, lstat,
access, chown, lchown, truncate, mkdir, rmdir, unlink,
rename (either side), link (either side), symlink (empty
linkpath and empty target — no link is created), readlink,
chdir, utimes, statfs, inotify_add_watch (valid fd), getxattr,
lgetxattr, mknod, execve. Controls all normal.

The deliberate exemptions, also measured:

- The AT_EMPTY_PATH fd forms work at newfstatat, statx,
  faccessat2, fchownat and utimensat: "" + the flag operates
  on the descriptor (a file descriptor works, not just a
  directory); a bad descriptor with the flag answers -EBADF.
- openat does NOT honour AT_EMPTY_PATH on this kernel:
  openat(dirfd, "", O_RDONLY|AT_EMPTY_PATH) answers -ENOENT,
  so no exemption is owed at open/openat.
- utimensat(NULL path) answers -EINVAL on this kernel with
  NULL times and with valid times — the NULL fd form does not
  work; "" + AT_EMPTY_PATH is the only fd form.
- Ordering compounds: inotify_add_watch(badfd, "") answers
  -EBADF (the descriptor is checked first); readlinkat(badfd,
  "") answers -EBADF (the dirfd is resolved first);
  symlinkat(target, badfd, "") and the renameat empty-side
  shapes answer -ENOENT (the empty answer precedes the second
  descriptor's resolution); newfstatat/statx/faccessat2 with
  a bad descriptor + "" + no flag answer -ENOENT (the empty
  answer precedes dirfd resolution).

## Where the fix sits, and why not the resolver

The resolver itself is not wrong for its internal callers:
`fszip.cpp` passes "" deliberately to obtain the root node,
and kernel-internal sites pass "" as the currentDirectory
argument with real paths. Refusing "" in
`Fs::getNodeFromLocalPath` would break those. The audit
therefore placed the refusal at the guest boundary, call by
call:

- At the KProcess method entries both dispatchers funnel
  into (open, openat, access, chdir, chmod, fchmodat, execve,
  stat64, lstat64, fstatat64, statx, rmdir, mkdir, mkdirat,
  rename, renameat, link, symlink/symlinkat, readlink,
  unlinkFile, unlinkat, utimes, utimesat, utimesat64,
  faccessat, inotify_add_watch, statfs, statfs64). Every
  KProcess path method's callers are only the two guest
  dispatchers and native tests with real paths; the one
  internal production caller of the lower funnel
  (openFile from cpu.cpp and initStdio) never passes "".
  Ordering follows the host: the guard is the first statement
  except at inotify_add_watch (after the descriptor check)
  and readlink (the worker is reached after readlinkat
  resolves its descriptor). The AT_EMPTY_PATH fd forms are
  exempted at fstatat64, statx, faccessat and utimesat.
- At the 64-bit dispatcher sites that bypass KProcess or
  join the path before calling it: sys_openat64,
  sys_stat_path64, sys_statx64 (in the non-AT_EMPTY_PATH
  branch, before dirfd resolution), sys_readlink64, and the
  open-coded access/faccessat/faccessat2 (faccessat2 +
  AT_EMPTY_PATH exempt), mkdir/mkdirat, symlink/symlinkat
  (both arguments), link/linkat (both arguments; linkat +
  AT_EMPTY_PATH on the old path exempt — the emulator does
  not implement that fd form, so its current answer is left
  untouched), unlink/unlinkat, and the utimensat and statfs
  stubs (a readable first byte of 0 answers -ENOENT; the
  stubs' success answers for real paths, null paths and the
  AT_EMPTY_PATH form are unchanged).
- At the 32-bit getxattr/lgetxattr pair, which resolved the
  path only inside the user.DOSATTRIB branch: an empty path
  now answers -ENOENT before the name check, as the host
  resolves the path first.

Not changed, deliberately: the shared resolver; both guest
string readers; the ignored 32-bit stubs that never resolve
a path (the chown family, mount, utime nr 30 — they return
0 for every path, a separate standing divergence outside
this defect's mechanism); the 64-bit xattr stub cases
(filed as FD-133).

One correction to the filing's framing: the 64-bit open call
already answered -ENOENT for an empty path on the base,
through its -1 dirfd sentinel hitting the
unsupported-relative-dirfd route. openat with AT_FDCWD was
the genuinely open shape (it returned a descriptor to the
working directory); the guard now answers for the stated
reason at both, and the tests pin open, openat against a
real dirfd, and newfstatat against a bad dirfd as standing
-ENOENT answers riding that route.

## Proof

Guest tests staged against an empty path at the
representative calls, on the unmodified base and with the
fix (evidence in `test-results/fd131/`):

- `testEmptyPath64Syscalls` (x64 suite): RED on the base —
  28 assertions failing with the base answers the audit
  predicted (an empty openat returning a descriptor to the
  working directory, stat/access/chdir of "" answering 0,
  mkdir "" answering -EEXIST, a symlink with an empty target
  created, statx with a bad descriptor answering -EBADF
  where the host answers -ENOENT) — and GREEN with the fix.
  Destructive shapes (unlink/rename of "") are staged last
  against sacrificial working directories, since on the
  base they act on the working directory itself.
- `testEmptyPathProcessApi` (main suite): RED on the base —
  34 assertions failing with the predicted answers (an empty
  open/openat returning a descriptor, chmod "" answering 0,
  rmdir "" answering -ENOTEMPTY) — and GREEN with the fix;
  pins the KProcess-level guards, the descriptor orderings,
  and the AT_EMPTY_PATH exemptions. Every control in both
  tests already passed on the base.
- Native suites serial, one worker, full runs: main 669/669
  and x64 91/91, 0 FAILED with the fix (`green-main.log`,
  `green-x64.log`); on the base the same runs failed only
  the two new tests (`red-main.log`, `red-x64.log`).
- JS unit suite (`runner.mjs --unit`) on the built tree:
  348 passed / 0 failed (`js-unit.log`).
- Browser build: BUILD COMPLETE, "Browser export verified"
  (`browser-build.log`); BUILD_INFO git_sha `a8d43046c`
  (the fix commit), git_dirty_files 0, wasm sha256

- Silent-failure audit: `tools/known-gaps-audit.mjs --check`

  through the existing idioms and add no counted site.

## New filings from this audit

- FD-132 — null path pointers are erased to "" before the
  empty-path route at the 32-bit reader (KMemory::readString
  returns empty for a null address by construction) and at
  the 64-bit dispatcher's open-coded path cases (the
  memcpyFromGuest copies in the access/mkdir/symlink/link/
  rename/unlink family carry no null guard): after FD-131
  those shapes answer -ENOENT where the host answers
  -EFAULT. The 64-bit helper-based calls and FD-126's two
  sites already answer -EFAULT. Reader-level fidelity is
  its own lane, per FD-126's reader-audit precedent.
- FD-133 — the 64-bit xattr cases (syscalls 188–199) answer
  without ever resolving the path (-ENODATA / 0 / -ENOTSUP
  for existent and nonexistent paths alike); the host
  answers -ENOENT for a path that does not resolve,
  including "".
- FD-134 — KProcess::statx substitutes the descriptor's
  path for a non-empty path whenever AT_EMPTY_PATH is set;
  the host stats the named path (the flag matters only for
  an empty path).
- FD-135 — the 64-bit statfs case ignores the path entirely
  beyond the empty shape FD-131 fixed: it answers 0 for
  nonexistent paths too, where the host answers -ENOENT.
