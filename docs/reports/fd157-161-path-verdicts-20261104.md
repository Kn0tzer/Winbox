## Host measurement first

All host behaviour was measured before any product change with
raw `syscall()` reference programs using the aarch64
asm-generic numbers (`test-results/fd157-161/hostref-fd157-161.c`
/ `.out`, plus `libcforms-fd157-161.c`); strace cross-checks
confirm the libc forms issue the same raw shapes (glibc
`getxattr` → `getxattr`, `readlink` → `readlinkat`, `rmdir` →
`unlinkat(AT_REMOVEDIR)`, `link` → `linkat`), so the raw

disagreed: `readlink("ld/")` → -EINVAL and `readlink("ln/")` →

## The five defects, by substance

### FD-157 — the 32-bit xattr path forms did not resolve

`getxattr`/`lgetxattr` resolved only for the one modelled name
(`user.DOSATTRIB`) and answered -ENOTSUP for every other name,
resolved or not; the other six path forms (setxattr 226,
lsetxattr 227, listxattr 232, llistxattr 233, removexattr 235,
lremovexattr 236) had no handlers at all and answered -ENOSYS
for every input. The host answers by resolution: a missing path
-ENOENT, a path through a file -ENOTDIR, an unresolved
attribute on a resolved file -ENODATA. The fix resolves every
name in get/lget (miss -ENOTDIR/-ENOENT, resolved -ENODATA) and
gives the six missing forms one shared helper that follows the
host's measured entry order — the set forms' flags word first
(-EINVAL for bits outside XATTR_CREATE|XATTR_REPLACE), a null
path -EFAULT, a null name -EFAULT, an empty path -ENOENT, then
resolution — answering -ENOTSUP (set/remove) or an empty list
(list) for a resolved target, the 64-bit dispatcher's standing
contract.

The host matrix also corrected the filing's own entry order:
the attribute name is fetched ahead of the path verdicts —
`getxattr("", NULL)` answers -EFAULT on the host, not -ENOENT —
so get/lget now check a null name before the empty-path
verdict. (The FD-132 pins are unaffected: a null name with a
resolvable path still faults; no existing pin combined an empty
path with a null name.)

### FD-158 — readlink of a missing path answered -EINVAL

Both resolver sites folded "no such path" into "not a link":
`KProcess::readlinkInDirectory` (32-bit readlink/readlinkat)
and `sys_readlink64` in the 64-bit dispatcher (readlink and
readlinkat). The host answers -ENOENT for a missing path and
keeps -EINVAL for a resolved non-link. Both sites now split the
two cases; the through-a-file -ENOTDIR case is unchanged.

### FD-159 — a trailing "/", "/." or "/.." through a file resolved to the file

Three different normalization steps erased the marker before
any lookup could judge it: `getFullPath` strips a trailing
"/.", the resolver walk skips the empty final part of a
trailing "/", and `cleanPath` erases a "name/.." pair. The host
answers -ENOTDIR for `a.txt/`, `a.txt/.` and `a.txt/..`
because the marker steps INTO the final component. The fix
judges the anchor inside `Fs::getNodeFromLocalPath`: when the
caller asks for the notDir verdict and the raw path ends in one
of the markers, the component before the marker is resolved
first — a non-directory anchor sets the notDir verdict, a
plain-missing anchor under "/.." misses (where the erased pair
used to resolve the rest of the path), a directory anchor falls
through to the ordinary walk. Only notDir callers pay for the
extra resolution. The same marker at readlink steps through the
link and judges its target (host-measured: a link to a
directory answers -EINVAL, to a file -ENOTDIR); both readlink
sites judge the followed anchor when the resolved node is a
link and the path carries a marker.

Implementation note: the resolver change is written with
`substr` suffix tests and the seven-argument overload because
the `fs-dynamic-link-cache` JS unit test compiles this function
out of the production source against a stub BString/Fs that
provides neither `endsWith` nor the five-argument overload;
the first form of the fix broke that harness's compile and was
rewritten in the common subset (the test passes on the final
form). Guest behaviour is identical.

### FD-160 — the 64-bit dispatcher's rmdir answered -ENOSYS for everything

Syscall 84 had no case. It now routes to `KProcess::rmdir`
like the 32-bit dispatcher and the neighbouring mkdir case,
with the null-path (-EFAULT) and empty-path (-ENOENT) verdicts
those cases carry; `KProcess::rmdir` already answers the
host's shape verdicts (empty directory 0, file -ENOTDIR,
missing -ENOENT, non-empty -ENOTEMPTY).

### FD-161 — a hard link to a bare filename answered -ENOENT

`Fs::getParentPath("hl.txt")` returned "hl.txt" itself:
`lastIndexOf` finds no slash (-1) and `substr(0, -1)` is the
whole string, so the destination's parent lookup resolved the
not-yet-existing destination and reported it missing. A
slash-less path is a bare filename in the working directory,
whose parent is that directory — the function now returns the
empty relative path for the slash-less shape.

Consumer audit (the filing's closing terms): the
absolute-path callers (executable lookup, open-create, mkdir,
rename's destination parent, symlink, the unix-socket bind
path, the startup-argument scan, the boxed container UI)
always hold a slash and are unchanged; the rename/renameat
inotify parent lookups take raw guest paths and now name the
working-directory node for a bare filename, matching the host;
the zip-mount caller is mount-prefixed; `makeLocalDirs("")` in
the local-directory builder is a verified no-op (it produces
no mkdir calls for the empty string); the fsfilenode rename
sites receive full paths. No other consumer depends on the old
slash-less answer.

## New filings from this lane's measurements

- FD-162 — the 32-bit xattr **descriptor** forms answer the
  emulator-private -EBADFD (77) for an unopened descriptor,
  where the host answers -EBADF (9); `flistxattr` answers
  -ENOTSUP without consulting its descriptor at all. The
  64-bit dispatcher answers -EBADF correctly, so this is a
  32-bit-only divergence, outside FD-157's eight path forms.
- FD-163 — an xattr name in an unmodelled **namespace**
  (measured: `getxattr(file, "bogus.x")`) answers -ENOTSUP on
  the host — the namespace is rejected before the attribute
  lookup — while both dispatchers answer -ENODATA for every
  unresolved name on a resolved file. FD-157's closing terms
  allowed -ENOTSUP to stay only where the host's -ENODATA is
  not the measured answer; for unknown-namespace names it is
  not, so the case is filed separately.
- FD-164 — the rest of the erased-".." family: a ".." away
  from the end of a path is disposed of textually by
  `cleanPath` without resolving the component before it, so
  `missing/../a.txt` resolves as `a.txt` (host -ENOENT) and
  `a.txt/../d` as `d` (host -ENOTDIR), and a bare ".." at the
  root answers -ENOENT in the guest where the host answers 0.
  This lane's guest tests print all three shapes as
  observations on the fixed tree (they still diverge: FD-159's
  fix judges only the trailing marker).
