## The run-native failure — FD-67 (registered, open)

FD-50's fix works in composition: the harness now passes the
pipeline-cache section that used to kill it (`PASS: former stubs (device
image sizing, queue2, granularity, sparse, pipeline cache, buffer-view
destroy)`) and executes 43 sections, including FD-16's SPIR-V audit
guards. It then aborts at FD-62's guard, first bridge-level assertion:
the guard's texel-atomic heap module must be refused with
VK_ERROR_FEATURE_NOT_PRESENT; the bridge returns **VK_SUCCESS** (measured
directly on a diagnostic build: verdict 0, no capability rejection
counted).

Root cause: FD-62's classifiers record the texel refusal in the array
verdict (`texelAtomicByVar`), and the JS mirror acts on its record
(spirvfix refuses the class by name — its suite passes on this tree).
The bridge's admission path (`vk64AuditSpirv`) never consults the
recorded verdict, so the two mirrors disagree and the module is admitted
at creation. This is a defect in FD-62's change as committed — its
wiring is incomplete — not a composition interaction, proven three ways:

1. The identical abort occurs in an isolated harness build using FD-62's
   own bridge (FD-61's delta reverted): 43 PASS lines, same assertion.
2. FD-62's lane tree cannot reach the guard at all — its harness still
   dies at FD-50's fn-921 call (fixture bounds assertion inside the
   pipeline-cache section, re-run 2026-11-01).
3. FD-50's lane tree, which has neither change, completes the harness
   (52 PASS, exit 0, re-run 2026-11-01).

A consequence for the record: FD-62's lane report claims a completed
standard-harness run including this guard (53 PASS lines, exit 0). That
claim is not reproducible from the committed tree, and the evidence
directory it cites is absent from that tree. The register's Section B
row for the lane described the guard's proof correctly (a scratch
harness). FD-62's register entry now carries a correction note pointing
at FD-67; FD-62 itself stays open on its original terms, and FD-67
carries the closing terms (bridge refuses the recorded texel class by
name at module creation, mirroring the JS verdict — or the sweep becomes
texel-aware — after which the guard passes as written or is corrected to
the implemented attribution, and run-native completes end to end).

No test, readiness rule, or register claim was weakened to pass this
gate; the guard and the audit stand as committed, and the failure is
reported as a failure.
