# FD-98 — 32-bit preadv/preadv2 wired; FD-99 and FD-100 filed

Branch `lane-fd98`, based on `lane-fd94-96` tip `a50afdada`
(itself off integration tip `cc1d89ab3`), so the read/write
family's register lineage stays in one line: this register
carries FD-83/FD-84 as filed, FD-94/FD-96 closed (CL-49/CL-50)
and FD-97 open from the sibling branch, and FD-98/FD-99/FD-100
were filed here first, before any code was written.

Commits: `79a6f5d28` (register filings + host reference
evidence), `8edaaaea2` (test), `86dfb5830` (fix + test staging
correction). Register: FD-98 closed here as CL-51
(provisional); FD-99 and FD-100 filed, open.

## The gap

The 32-bit syscall table carried nullptr at slot 333
(preadv) and slot 377 (preadv2): every call answered
-ENOSYS. The 64-bit dispatcher has had preadv since FD-80,
and FD-94 wired the write-side twin (pwritev 334/378) while
recording these two slots as the read family's, deliberately
untouched there. FD-92's 32-bit readv (145) exists only on
lane-fd92-93 and is not in this base; nothing in this lane
depends on it.

## Host contract, measured fresh

Dedicated reference programs were run on the box's host
kernel (6.17.0-1020-oracle) before any code was written:
`test-results/fd98/hostref-preadv.c` (the full matrix,
including IN_ACCESS counts via inotify),
`hostref-preadv-order2.c` (the flags-vs-array discriminator)
and `hostref-pwritev-order.c` (the same discriminators for
the write side, measured for FD-100). Results:

- Segments fill in order at successive offsets; the file
  position does not move for explicit offsets; a short read
  ends the walk; a zero-length segment is skipped; a later
  segment's failure returns the bytes already read (a good
  4-byte segment plus a bad-buffer segment returns 4); a
  failing first segment returns the error (-EFAULT).
- Exactly one IN_ACCESS per successful call, including
  0-byte successes: at EOF, with iovcnt 0, and with
  all-zero-length segments. Failed calls generate none.
  This is FD-83's contract, now confirmed for the
  positioned vectored reads as well.
- Validation order, every step measured against its
  neighbours (both directions agree):
  1. Offset: preadv answers EINVAL for any negative
     offset; preadv2 answers EINVAL only below -1 —
     offset -1 is the file-position mode (measured: a
     read at position 5 returned the bytes at 5 and left
     the position at 9). The offset check precedes the
     descriptor check (bad fd + offset -1/-2 → EINVAL),
     except that preadv2's legal -1 lets the descriptor
     check fire (bad fd + -1 → EBADF).
  2. Descriptor: a bad descriptor answers EBADF.
  3. Mode: a descriptor that cannot be read answers
     EBADF — ahead of the iovcnt range check (WRONLY +
     iovcnt -1 → EBADF), ahead of the flags check
     (WRONLY + undefined flag → EBADF), and ahead of an
     iovcnt-0 success return (WRONLY + iovcnt 0 → EBADF).
  4. iovcnt range: EINVAL outside 0..1024 — ahead of
     the flags check (iovcnt -1 + undefined flag →
     EINVAL, both directions).
  5. Iovec array: EFAULT for a null or unmapped array
     with iovcnt > 0 — ahead of the flags check (null
     array + undefined flag → EFAULT).
  6. Flags (preadv2 only): EOPNOTSUPP for bits outside
     the defined RWF mask, which on this kernel is
     0x3f for reads too — bits 0x01..0x20 are all
     accepted (0x20/NOAPPEND included, meaningless on a
     read), 0x40 is refused. The flags check runs last.
- A directory descriptor answers EISDIR; a pipe answers
  ESPIPE (see the boundary note below).

## The FD-95 interaction (recorded as required)

FD-95 (filed on lane-fd92-93) holds the read family's
(bad descriptor, negative offset) combination open: the
host answers EINVAL (the offset check precedes even the
descriptor check), but FD-84's composed fix on
lane-fd83-84 orders the descriptor check first in
sys_pread64Impl and sys_preadv64, so the composed 64-bit
read family answers EBADF for that pair, and
KProcess::pread64 carries no offset check in either
shape. FD-95 leaves the read side's final composition to
the merge lane.

This wiring takes the host's side, deliberately: the
offset check in KProcess::preadv runs before the
descriptor check, so the 32-bit preadv/preadv2 pair
answers EINVAL for (bad descriptor, negative offset) —
the same side FD-93 took for the write family's
positioned calls and FD-94 implemented in both pwritev
wirings. The new test pins the pair explicitly
(`invoke(333, 9999, 1, -1, -1) == -EINVAL`, and the
preadv2 -1/-2 split). Consequences, stated plainly:

- Until FD-95 is settled, the two dispatchers' read
  families disagree on this one combination: 32-bit
  preadv EINVAL (host), 64-bit preadv EBADF (FD-84's
  order). The disagreement predates this lane (it is
  FD-95 itself); this lane adds no new divergence, it
  declines to copy the non-host one into new code.
- If the merge lane settles FD-95 offset-first (the
  host's order), FD-84's two 64-bit sites flip and this
  wiring stands as the family shape. If it settles
  descriptor-first, the offset check in
  KProcess::preadv moves behind the descriptor check —
  a one-line reorder in one function — and the pinned
  case in testPreadv32Dispatch flips with it. Either
  settlement is mechanical from here.

A second, smaller interaction of the same kind: this
wiring's mode gate answers EBADF (the host's answer,
FD-84's destination) from its own check, ahead of
FD-84's in-flight fix to the shared core. Once FD-84
composes, the per-segment core (one of FD-84's five
named sites) answers EBADF itself and the two agree;
the gate stays correct under either composition order.

## Also filed here

- **FD-99** — the 64-bit preadv2 arm of the composed
  sys_preadv64 (FD-80) refuses two things the host
  accepts, both measured by this lane's reference
  programs: preadv2's offset -1 (it answers EINVAL for
  any negative offset; its header comment records the
  -1 refusal as measured behaviour, which the fresh
  measurement contradicts for preadv2 — preadv itself
  does answer EINVAL at -1) and flag bit 0x20 (its mask
  is 0x1f; the host's read mask is 0x3f). FD-98's 32-bit
  wiring implements the measured behaviour; the 64-bit
  fix shape is recorded in the entry.
- **FD-100** — the family's three wired implementations
  (sys_preadv64, sys_pwritev64, KProcess::pwritev) all
  run the v2 flags check ahead of the iovcnt range and
  iovec array checks; the host runs it last (measured
  both directions: iovcnt -1 + undefined flag → EINVAL,
  not EOPNOTSUPP; null array + undefined flag → EFAULT,
  not EOPNOTSUPP). Two combinations diverge; every other
  measured combination agrees. FD-98's wiring uses the
  measured order.

## The fix

- `include/kprocess.h`: KProcess::preadv declared next
  to KProcess::pwritev.
- `source/kernel/kprocess.cpp`: new KProcess::preadv,
  mirroring KProcess::pwritev's shape (FD-94) — offset
  check first (with preadv2's -1 file-position mode,
  which walks at the current position and advances it
  by the bytes read), descriptor and mode checks
  (EBADF), iovcnt range (EINVAL), iovec array range
  check (EFAULT), flags check last (EOPNOTSUPP outside
  0x3f, preadv2 only); the walk calls
  this->pread64 per segment at successive offsets,
  skipping zero-length segments, ending at a short
  read, returning the accumulated bytes when a later
  segment fails. The notification raise follows
  FD-92's readv shape: per-segment reads notify
  through FsOpenNode::read when bytes move and the
  inotify queue coalesces them into one observable
  event, so KProcess::preadv raises
  KInotify::notifyAccessed itself only when a
  successful call moved no bytes.
- `source/kernel/syscall.cpp`: syscall_preadv /
  syscall_preadv2 wrappers mirroring syscall_pwritev /
  syscall_pwritev2 (offset as the lo/hi register pair,
  flags in the sixth argument for preadv2), and table
  slots 333/377 filled.

## Boundaries and deliberate non-goals

- Pipe descriptors: the host answers ESPIPE for
  preadv on a pipe; the walk inherits the shared
  positioned core's -EINVAL for non-file types
  (KProcess::pread64 answers ESPIPE only for
  sockets). 32-bit pread64 has the identical answer
  today; the divergence lives in the core, not in
  this wiring, and is recorded in FD-98's register
  entry with the measurement.
- Neither vectored-read walk implements the host's
  total-length-overflow EINVAL; the trait is shared
  with sys_preadv64 and both readv walks and was
  already characterised by the FD-92/93 lane
  (inseparable from the per-segment length handling
  the family documents). Not re-filed.
- FD-99 and FD-100 are filed, not fixed: they belong
  to the composed 64-bit dispatcher and to FD-94's
  in-flight branch respectively, and fixing them
  here would have put this lane's diff into three
  other implementations' validation blocks.
