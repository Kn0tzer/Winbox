# FD-06 — 32-bit port IO and int 0x99 fault delivery (2026-10-31)

Branch `lane-fd06-portio` (worktree `wt-fd06`), base integ tip
`c4bab5e07`. Fix commit `d88fdc61a`. Nothing pushed, live site
untouched.

## The decision being implemented

Frontier review D9 (`test-results/frontier-review-20261031/REVIEW.md`,
coordinator-adopted): deliver #GP through `CPU::prepareException`
for the 32-bit port-IO panics and for `int99` on an unregistered
callback index, with error code `(vector<<3)|2` for int99,
mirroring the x64 INT fix. The one factual input the review left
open: what `syscall_ioperm`/`iopl` currently return.

## The open question, settled first

Both permission calls return success while granting nothing:

- `syscall_ioperm` (source/kernel/syscall.cpp) logs the request
  as IGNORED and returns 0; `KSystem::syscall_ioperm`
  (source/kernel/ksystem.cpp) returns 0 unconditionally.
- `syscall_iopl` likewise logs IGNORED and returns 0.

There is no permission bitmap and no permitted-port set anywhere
in the emulator, so no port access is ever permitted and a
0xFF-fill for "permitted" ports could never be the honest model.
#GP(0) for every port instruction is the only answer consistent
with the permission calls' actual behaviour.

## A correction to FD-06's evidence

FD-06 named `source/emulation/cpu/ops.h` (the twelve INS
handlers, the int99 handler). Those panics exist in that file
exactly as reported — but **no translation unit in the tree
includes ops.h**: a tree-wide search over `source/` and
`project/` finds it referenced only by a comment in a test,
which itself calls it "the legacy ops.h", and the built native
test binary contains neither panic string. The live sites were:

- **Port IO:** the six string port ops (INSB/INSW/INSD/
  OUTSB/OUTSW/OUTSD) decode normally but have no handler in
  the (only) 32-bit core, `NormalCPU` — unassigned ops fall to
  `normal_invalid`, i.e. SIGILL, not the #GP hardware gives for
  an unpermitted port access. Wrong fault, delivered the wrong
  way, for every guest that touches a port.
- **int 0x99:** `normal_int99` (and `common_int99`) call
  `callOpenGL` (source/opengl/glcommon.cpp), whose unregistered-
  index path was a bare `kpanic_fmt` — the live guest-reachable
  emulator kill FD-06 described, one file over.

Both are fixed at the live sites. ops.h itself was left alone:
it is not compiled, so editing it could not be verified, and
marking this entry fixed on the strength of a dead file would
have been a false closure.

## What changed (commit `d88fdc61a`)

- `NormalCPU` gains `normal_portIoFault`
  (`prepareException(EXCEPTION_GP, 0)` + `NEXT_DONE()`, the
  existing privileged-instruction shape), wired for all six
  string port ops in **both** dispatch mechanisms: the
  `normalOps` table and the `normalDispatch` switch.
- `callOpenGL` returns bool. A registered callback runs exactly
  as before. An unregistered index delivers
  `prepareException(EXCEPTION_GP, (0x99<<3)|2)` and returns
  false; `normal_int99` then continues at the redirected EIP
  (`NEXT_DONE()`) instead of falling through, and
  `common_int99` propagates the result. When no handler exists,
  the delivery machinery ends the guest process — the emulator
  keeps running.

## Proof

New test `testPortIoFault32` (source/test/cpu/), registered in
testMain: executes INSB, INSW, INSD, REP INSB, OUTSB, OUTSW,
OUTSD, and int 0x99 with an unregistered stack index against a
guest SIGSEGV handler, and pins signal = SIGSEGV, trap = 13,
error = 0 for the port forms and (0x99<<3)|2 for int 0x99.

- **On the pre-fix code** (fix files stashed, test kept): every
  port case delivers SIGILL instead (`guest-ill32 ... delivered=1`
  lines, SIGSEGV assertions unmet), and the int 0x99 case kills
  the test binary with the old panic text
  `Uknown int 99 call: 16777215`, exit 1. (An earlier unhardened
  version of the test hung on the pre-fix code — SIGILL's default
  disposition ends the fixture process and the run loop spins;
  the test now catches SIGILL on a stub handler so a regression
  fails cleanly rather than hanging the suite.)
- **On the fixed code:** the test passes standalone and in the
  suite. Native suite accounting on this branch, run serially:
  650 of 661 tests pass in a single run before the run enters
  the pre-existing tail diagnostic flood (below); the remaining
  window (indices 648–660) passes standalone 13/13, so all 661
  tests — 660 at the base tip plus this one — pass on this
  branch, with 0 failures recorded anywhere.

## Found, not fixed (registered as FD-39 and FD-40)

Both convicted by A/B against the pristine base tip during this
lane; neither is in code this lane touched.

- **FD-39:** running native tests 610–621 aborts
  (`terminate called after throwing an instance of 'int'`,
  rc 134) in the clone test group after the syscall-ABI block,
  identically on the pristine base and on this branch; the same
  tests pass standalone. A preceding-test interaction, not a
  deterministic failure.
- **FD-40:** a full serial suite run can enter an unbounded
  crash-diagnostic flood ("probably about to crash, could not
  find emulation instruction that caused exception") in the
  tail tests after ~650 passes, growing the log by gigabytes;
  the same flood aborted a deploy-gate attempt on the shipped
  tree (recorded in `docs/reports/deploy-20261031.md`), and the
  tail tests all pass standalone. The flood itself — a
  diagnostic path with no rate limit — is exactly the class of
  failure the cleanup campaign's logging standard exists to
  prevent.
