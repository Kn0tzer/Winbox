# FD-169 — CRT family: 1,634 placeholder functions genuinely implemented

Lane record, 2026-11-05/06. Branch `lane-fd169` (base: the DLL-export
census lane tip). Register entry FD-169 covers 10,698 validated
unimplemented stubs across 65 Microsoft C/C++ runtime tables. This
lane discharges the C-runtime family — the nine DLLs whose
implementations live in Wine's `dlls/msvcrt` source (msvcrt,
msvcr70/71/80/90/100/110/120, ucrtbase) — on both architectures:
**1,634 stubs resolved (916 x86-64 + 718 i386), zero new stubs, zero
lost exports.** FD-169 stays open for the remaining families
(C++ libraries, concurrency runtime, mixed-mode assemblies,
vcruntime), each with its reason recorded below.

## What was implemented

One source tree drives all nine DLLs per architecture, so each
implementation below lands in every DLL whose spec carries the name.

Backports from upstream Wine (post-8.0 master; the functions exist
upstream but the shipped Wine 8.0 / 10.0 builds still stub them):
the `_mbs*_l` multibyte locale family (24 functions) and their
`_o_` ucrtbase aliases, `_mblen_l`, `__iswcsym`/`__iswcsymf`,
`_aligned_recalloc`, `_aligned_offset_recalloc`, `_cprintf_l`,
`_cwprintf_l`, `_wprintf_l`, `_vwprintf_l`, `_fprintf_s_l`,
`_FCbuild`, `cimag`/`cimagf`/`crealf`, `feholdexcept`, `imaxdiv`.

Hand-written for this lane (no upstream implementation exists):
the `_ismbb*` classification family (the MS Learn defining
expressions over Wine's mbctype table), `_ismbcblank`,
`_mbsncoll`/`_mbsnicoll` (+`_l`), `_mbsninc_l`, `_mbstrnlen`,
`_mbsstr_l`, the secure `_mbsset_s`/`_mbsnset_s`/`_mbsnbset_s`/
`_mbsncat_s` forms, `__p__mbcasemap`; the MSVC complex helpers
(`_Cmulcc`, `_Cmulcr`, `_FCmulcc`, `_FCmulcr`, `_LCbuild`,
`_LCmulcc`, `_LCmulcr`) and the C99 complex set (`cabs`…`ctanh`
incl. `carg`/`cimag`/`conj`/`cproj`/`creal`, float and
long-double variants — the `l` variants compute in double
precision by design, since MSVC's long double is 64-bit while
Wine's is 80-bit, so results are exact for the MSVC ABI); the
positional/secure printf public forms (`_printf_p`, `_printf_s`,
`_vprintf_p`, … and wide/console equivalents plus the
`__conio_common_vc[w]printf_p/_s` entry points — Wine 8.0's
formatting engine already supports the semantics, the public
entry points were missing); the `scanf` family entry points
(`vscanf`, `vscanf_s`, `vfscanf_s`, `vsscanf_s`, … and
`__conio_common_vc[w]scanf`); console input (`_cgets_s`, `_cgetws`,
`_cgetws_s`, `_getws_s`); the UTF-16/32 conversion set
(`mbrtoc16`, `mbrtoc32`, `c16rtomb`, `c32rtomb`);
`_findfirst32i64`/`_findnext32i64` (+wide); `_umask_s`,
`_lsearch_s`, `_strset_s`, `__wcsncnt`, `__iswcsym_l`,
`__iswcsymf_l`.

Spec-only resolutions (the implementation already existed in the
tree; only the export was a stub): the `wcstoimax`/`wcstoumax`
aliases, and the `_o_` mirrors of newly real functions in
ucrtbase (85 on x64, 60 on x86).

Guest-level proof (suite browser tests fd169-crt64 and
fd169-crt32; fixtures tools/guest-fixtures/fd169-crt64.c and
fd169-crt32.c, 54 behavioural checks each):

- x86-64: PASS, fixture prints "fd169-64: RESULT 0 (54 checks)".
  Groups: ismbb (CP932 classification from Wine's mbctype table),
  the _mbs*_l string family, the hand-written mbcs collate /
  secure-set functions, C99 complex + the MSVC complex helpers
  through ucrtbase (and the members msvcr120 exports), printfp,
  scanf, find (_findfirst32i64 over System32), uchar (UTF-16/32
  conversion incl. surrogate pairs), misc (_aligned_recalloc
  growth with zero-fill, _umask_s, _lsearch_s, _strset_s,
  feholdexcept, imaxdiv, wcstoimax), and a resolve group proving
  all 258 flipped ucrtbase exports are present at runtime.
- x86: PASS, "fd169-32: RESULT 0 (54 checks)", 205-name resolve
  list; run twice (before and after a fixture correction below),
  passing both times.
- Negative control (x86-64): the same test against the retained
  pre-change wine64.zip (sha256 be4d4956b9cc93f0a1da0c2086f490d1
  dec9bb749ba48382d10ea9e633963cee) FAILS as designed: the fixture
  aborts in its first group with "wine: Call from 000000007B013456
  to unimplemented function ucrtbase.dll._ismbbkpunct, aborting"
  and never prints a RESULT line. The FD-169 runtime was then
  restored (wine64.zip sha256 14e1dc80beb8453c578f2ab561ec1a93f4
  8ea2e64eccb2755e1a92f94c6ffec4), the browser export rebuilt
  (completeness gate 0 failures) and fd169-crt64 re-run: PASS.
  No retained pre-change wine32.zip exists, so the x86 negative
  rests on the census's binary-level stub detection of the
  shipped x86 DLLs rather than a re-run.
- Two fixture lessons worth keeping: (1) _printf_p, vsscanf_s and
  the other public _p/_s forms are NOT ucrtbase.dll exports, in
  Wine or in real UCRT -- they are import-library wrappers over
  __stdio_common_vfprintf_p / __stdio_common_vsscanf. The fixture
  proves that group the way real programs reach it: msvcr120's
  genuine _printf_p export prints the positional "hello world"
  line, and ucrtbase is exercised through
  __stdio_common_vsprintf_p / __stdio_common_vsscanf. The hand
  implementations of the public forms serve msvcrt and
  msvcr70..120, whose specs do carry them as exports.
  (2) Locale handles are private to each CRT: the fixture
  originally passed a ucrtbase _locale_t into msvcr90 and read a
  garbage result; it now passes NULL there. The fixture also
  initially called _aligned_recalloc with three arguments
  instead of its true four (num, size, alignment); corrected in
  both fixtures, with a zero-fill assertion added.

## What remains in FD-169, and why

Of the 10,698: 1,634 resolved here; 1,311 remain in the nine CRT
DLLs above; ~7,750 sit in other families:

- The same nine DLLs' remainder (1,311): `_getsystime`/`_setsystime`
  (the offset parameter's contract is not publicly pinned; a wrong
  clock-setter is worse than a loud stub), the `_mbcasemap` data
  export (a stable global array cannot honestly back Wine's
  per-thread mbcinfo; `__p__mbcasemap` is implemented instead),
  the `_d`/`_f`/`_ld` libm helpers (20, contracts not publicly
  specified), `_freea` (the `_malloca` header layout is not
  modelled in Wine's heap), `_heapused`/`_get_winver`/`_initptd`
  and similar (would require fabricated values), `__crt*` Ex
  helpers and EH/NLG/type_info compiler plumbing (no honest
  independent contract; a wrong implementation corrupts exception
  handling globally), debug-heap `_Crt*` in msvcrtd (its
  bookkeeping is not modelled; returning success would lie).
- msvcp60/70/71 (~2,300): legacy pre-2010 STL ABIs — separate full
  implementation surfaces, not a draw-down of this kind.
- msvcp90-source family remainders (in msvcp90–140): codecvt
  facets, `_Yarn`, iostream move constructors, `time_get`
  internals — deep C++ ABI work, a separate effort.
- msvcp140_2 `__std_smf_*`: special mathematical functions
  (Bessel/elliptic/hypergeometric) carry a correctness burden a
  stub-draw-down cannot honestly meet without a dedicated
  numerical validation pass.
- msvcp140_atomic_wait (`__std_atomic_*`, `__std_tzdb_*`): the
  time-zone database has no data source in the browser build.
- concrt140 + the concrt names inside msvcr100/110/120 (~400): the
  Concurrency Runtime is a whole scheduler subsystem.
- msvcm80/90 (~528): mixed-mode C++/CLI assemblies; they cannot
  exist as honest native DLLs in this environment.
- vcruntime140 family: exception-handling machinery — see above.

Composition note: FD-167, FD-168 and this lane all extend the same
pipeline surfaces (backport DLL lists, zip staging lists,
`runtime-assets.json`, the census baseline, completeness pins,
`build-wine32-base.sh`); textual conflicts at merge time are
expected and mechanical — the substance composes disjointly
(distinct DLL sets and pin tables).
