# FD-168 win32u stub draw-down, slice 2 — five more real implementations

Lane: `lane-fd168-slice2` (worktree `wt-fd168-slice2`), off integration
tip `faf95d26c`. Date: 2026-11-07. All counts in this record are
lane-local until the batch-10 composition audit settles them; FD-168
stays open and no closure (CL) is claimed.

## What shipped

Five more x86-64 `win32u.dll` exports that shipped as validated spec
stubs are now real syscall implementations, in the Wine 8 backports
build: patch `tools/buildWine/patches/wine8-win32u-fd168-slice2.patch`
(applied after the slice-1 patch in
`tools/rootfs64/build-wine8-backports.sh`'s PATCHES list; the win32u
syscall table grows 289 -> 294 entries):

- `NtUserGetQueueStatusReadonly` — the existing `get_queue_status`
  wineserver request issued with `clear_bits = 0` instead of the
  requested mask, with the same flag validation
  (`~(QS_ALLINPUT|QS_ALLPOSTMESSAGE|QS_SMRESULT)` ->
  `ERROR_INVALID_FLAGS`) and the same changed/wake packing as the
  clearing sibling. The tree's own `get_input_state()` already peeks
  the queue exactly this way; the export was the missing piece.
- `NtUserIsTopLevelWindow` — `NtUserGetAncestor( hwnd, GA_ROOT ) ==
  hwnd`, the identity `dlls/win32u/window.c` already uses internally
  for the same question; NULL is rejected up front.
- `NtGdiCombineTransform` — the existing `combine_transform` helper
  (the same formula gdi32's `CombineTransform` computes) behind the
  NULL-argument checks, returning TRUE/FALSE like the gdi32 contract.
- `NtGdiGetCharSet` — returns the charset `NtGdiGetTextCharsetInfo`
  computes for the DC (the value gdi32's `GetTextCharset` exposes;
  an invalid DC yields `DEFAULT_CHARSET` through the existing path).
- `NtGdiPolyTextOutW` — loops the existing `NtGdiExtTextOutW` over
  the `POLYTEXTW` array, entry for entry the way gdi32's own
  `PolyTextOutW` does (including the cp=0 argument gdi32 passes).

Each was chosen because its semantics are fully determined by
machinery this tree already has — no new wineserver requests (the
server ships from the vendor build), no invented contracts, and no
upstream FIXME semi-stub bodies ported.

## Build notes (for the next win32u lane)

- **Blast radius kept to the win32u pair.** This lane's backports
  build ran from scratch (no persistent `/tmp/wine8-backports-build`
  existed), and a from-scratch rebuild does NOT reproduce the other
  40 outputs' pinned bytes: a 15-file family differs only in PE
  clock/checksum fields, but the DLLs whose patches went through
  iterative lane builds (combase, kernelbase, ntdll, the CRT family,
  mscms, ucrtbase, the vcomp family, user32, and a few more) differ
  in real content bytes — their shipped bytes were produced by
  incremental builds on trees carrying intermediate patch states.
  Rebuilding them here would have silently replaced reviewed bytes
  with unreviewed ones, so after the build the lane restored the
  other 40 outputs to their previous bytes (`git checkout`) and
  shipped only the new `win32u.dll`/`win32u.so` — the same
  two-binary shape slice 1 shipped. A composition that rebuilds the
  backports must expect the same drift and re-pin deliberately.
- **Do not export the sysroot `LDFLAGS` for the whole build
  script.** The `-Wl,-rpath-link,...` the unix tree's freetype link
  test needs also leaks into the native tools configure's PE probe,
  where `lld-link` rejects `-rpath-link` (fatal under `-WX`), and
  the build dies in the tools configure with a misleading "PE
  cross-compilation is required for ARM64" error. This lane ran the
  script without `LDFLAGS` (tools + PE trees complete; the unix
  configure then stops at its freetype probe, as the script's
  header describes), configured the unix tree itself with the
  script's exact configure line plus the `FREETYPE_*`/
  `FONTCONFIG_*`/`LDFLAGS` sysroot environment, and re-ran the
  script to finish (all three configures are skipped once their
  Makefiles exist).
- **Store vintage.** Prepping a `faf95d26c`-based tree against the
  shared store currently fails its pin check: the store was
  refreshed to the FD-188 runtime vintage after batch 9. This lane
  used a private store under `winbox-project/staging/` (removed at
  closeout) holding the batch-9 zips recovered from the retained
  `backups/winbox-runtime-assets-20261106/` archive. One gap the
  store check did not catch: `prefix64.zip` — the lane replaced its
  copy with the batch-9 bytes from the same archive (sha256
  `b1bfa64e...`) before restaging. A composition must settle the
  store vintage; this lane's runtime is based on the batch-9
  vintage and its win32u pair is the durable artifact (the patch
  rebuilds it on any vintage).

## Candidates examined and refused

Re-checked against the patched Wine 8 source, and refused for the
same standing reasons (nothing faked): the DPI point transforms
(`NtUserLogicalToPhysicalPoint` and kin — thread-DPI vs window-DPI
contract ambiguity, and identity at the guest's 96 DPI makes any
proof vacuous); `NtUserGetDpiForCurrentProcess` (contract not
pinnable from this tree); the ShutdownBlockReason trio (no
per-window string storage model in this vintage; user32's are stubs
too); `NtUserGetGuiResources` (the USER-object count has no source
in this tree — a half answer would fake `GR_USEROBJECTS`);
`NtUserSBGetParms` (no `SBPARAMS` type anywhere in the tree);
`NtUserQuerySendMessage` (no `SEND_MESSAGE_INFO` in the headers);
the ICM family including `NtGdiSetIcmMode` (no ICM state in
win32u's DC; gdi32's `SetICMMode` is itself a hardcoded FIXME);
`NtUserGetComboBoxInfo`/`NtUserGetListBoxInfo` (implemented PE-side
in user32 via control messages; no win32u-side state exists);
`NtGdiEnumObjects` (callback-from-syscall semantics do not map onto
this tree's syscall layer); the `NtUserCallHwnd*` lock/safe variants
(the win32k dispatch-index tables are not in this tree); the Eng*/
FONTOBJ/STROBJ display-driver DDI surface (no driver model); and
the eight upstream FIXME semi-stubs and six machinery-blocked names
already dispositioned in the FD-168 register entry.
