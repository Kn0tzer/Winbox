## FD-33 — the native release build does not build

RED (base `4006ddb58`, log `release-base.log`): `make release` compiles
the full tree, then the link fails with exactly the filed symbols:
`msgScratch(KThread*)` (from syscall.cpp, two sites),
`tickXWirePresent()` and `hasMainThreadWork()` (from
threadedMainloop.cpp). No compile error appeared anywhere in the build.

Cause, read from the sources: `msgScratch` was defined in
syscall64.cpp inside the file-wide `BOXEDWINE_GUEST_X64` gate, while
the 32-bit dispatcher's sendmsg/recvmsg slow paths in syscall.cpp call
it unguarded — it is 32-bit-guest infrastructure that the 64-bit
dispatcher also reuses for its message bounce. Only the test build
linked, because test_bridge_stubs.cpp substituted a stub returning 0
(its comment says so), which made the test build silently exercise a
fallback path instead of the real scratch. `tickXWirePresent` /
`hasMainThreadWork` are defined in xwirepresentSDL.cpp (wholly
64-bit-gated); the single-threaded mainloop already guards its call
with the same gate, the multi-threaded one did not.

Fix (`05ab65469`):
- syscall64.cpp: the message-scratch block (layout constants, the two
  per-thread scratch caches, their mutex, `msgScratch`,
  `bw64InvalidateScratchForThread`) moves ahead of the
  `BOXEDWINE_GUEST_X64` gate, with a comment recording why. The
  sockaddr bounce function itself stays gated (its only callers are
  the 64-bit dispatcher).
- kprocess.cpp: the execve scratch invalidation is no longer gated.
  The function now exists in every configuration, and a 32-bit execve
  previously left stale scratch entries in non-64-bit builds — the
  same stale-scratch fault the comment there describes, now closed
  for both guest widths.
- threadedMainloop.cpp: the wire-present calls are guarded with
  `BOXEDWINE_GUEST_X64`, mirroring the single-threaded mainloop. The
  wire sink is never installed in other configurations, so behaviour
  there is unchanged.
- test_bridge_stubs.cpp: the msgScratch stub is deleted; the test
  build now links the real scratch (the gl/vk bridge stubs and the
  mainloop stubs, which are genuinely absent from that build, stay).

Part (b) of the filing (a JIT compile error in the release
configuration): NOT REPRODUCED on this tree, and closed on that
basis. The two places a WASM-JIT threshold helper is used outside the
WASM JIT configuration already carry the guard
(`jitCodeGen.cpp` uses `wasmJit32HotThreshold()` only under
`BOXEDWINE_WASM_JIT` with an explanatory comment and a `JIT_RUN_COUNT`
fallback; `normalCPU.cpp` likewise, and the helper's declaration and
definition are both inside the gated wasmJitRuntime files). The full
release compile — every translation unit in the configuration —
completes with no error, which is the direct check.

GREEN: `make release` links; `Build/Release/boxedwine` (10,759,048 B)
starts, parses its command line and shuts down cleanly. The same
commit also builds in every other native configuration of
project/linux: `make test` (exit 0), `make x64-test` (exit 0),
`make x64` (exit 0; binary 5,679,864 B), `make x64-cache` (exit 0;
binary 5,681,888 B). Browser build below.

## FD-32 and FD-31 — parallel native suite runs die

The harness's multi-worker mode ran tests on std::threads inside one
process. FD-41 already established why tests cannot share a process
even sequentially (leaked guest processes/threads keep executing and
fault under later tests) and made the serial mode fork one child per
test; the threaded mode shared everything, concurrently.

RED (harness thread path preserved behind `BW64_TEST_NO_SHARD=1` on
the fixed tree — the code path is byte-for-byte the base's):
- Test suite, 4 workers: exit 139 after 2 tests OK, the log ending in
  a runaway guest-memfault loop (one BW64-FAIL line's count past
  26,624) — a leaked guest thread spinning in the shared process
  (log `runs/test-threaded4-red.log`).
- X64Test suite, default workers (4): exit 139 after 79 of 111 tests
  OK, the last output in the clone3 test neighbourhood — FD-31's
  filed shape (its ~33 count was under a different harness
  arrangement; the death point of a race varies by run, as FD-32's
  batch-4 addendum already recorded: ~47–65 there)
  (log `runs/x64-threaded-red.log`).

Fix (`05ab65469`, testCPU.cpp only): process sharding. In
`testRunParallel`, a multi-worker run on Linux/POSIX now forks
workerCount shard processes; each shard takes a strided slice of the
entries and runs it through the serial suite's own isolated path —
extracted unchanged into a helper, so every test still executes in
its own forked child of a process holding only its slice's history.
A shard's stdout/stderr go to a per-shard file the parent replays in
shard order after the shard exits; the shard's failure count returns
over a pipe. A shard that dies before reporting fails every test it
owned, loudly, so the final total can never silently shrink. If a
shard cannot be set up, its slice runs serially in the parent rather
than being dropped. `BW64_TEST_NO_SHARD=1` restores the thread path
for bisection; non-Linux platforms keep the thread path. The serial
path itself is the same code, moved, with the same verdict lines and
counting (its harness-failure branches now also bump the helper's
return count, which the serial caller ignores).

GREEN (logs in `runs/`):
- Test serial (1 worker): 686 tests, 0 FAILED (510 s, load ~12).
- Test 4 shards: 686, 0 FAILED (341 s). Test default invocation
  (worker count = hardware concurrency = 4 shards): 686, 0 FAILED
  (662 s, run concurrently with the x64-test build).
- X64Test serial: 111, 0 FAILED (28 s).
- X64Test default (4 shards): 111, 0 FAILED (22 s).
- X64Test 4 shards, three runs: 111 with 1 FAILED once, then 111/0,
  111/0. The single failure was the futex wait/wake race test
  ("lost a wake", wake=0 wait=0) in the first of two back-to-back
  full-suite runs at load 13–17; the same test passes 6/6 standalone
  serial at load 17.5 and in every other full run on this list,
  serial included. Recorded here as a load-sensitive race-test
  flake, with the failing log preserved
  (`runs/x64-shard4.log`), not as a shard-mode defect: sharding
  changes which process a test runs in, not the guest futex
  machinery, and the failure did not repeat in two further
  identical runs.

Totals in every completed mode equal the serial totals at this
composition (686 and 111 — the batch-7 gate's numbers), so parallel
verification now produces the same verdicts as the serial gate mode,
in roughly a third to two-thirds of the wall time on a loaded box.
