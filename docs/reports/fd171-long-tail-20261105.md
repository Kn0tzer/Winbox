# FD-171 — the stub long tail, dispositioned and drawn down (2026-11-05)

Lane: `lane-fd171` (worktree `wt-fd171`), based on `lane-dll-census`
tip `1e0a37f99` (the census change on integration `48d27952a`).

## What FD-171 covered

14,287 validated winebuild-stub exports across 535 shipped DLL
tables — the long tail left after FD-168 (win32u), FD-169 (CRT) and
FD-170 (whole-DLL-absence tables) took their partitions — plus the
standing guard: the export census fails on any new stub, and a
resolved stub is recorded by regenerating the baseline.

## Method

Every one of the 14,287 was classified against upstream Wine master
(`c42c1532a8b8a767d5e23b527ea874368c202ed0`, sparse clone):

- **583** have a body in upstream master. Each candidate body was
  screened by eye before porting: a body counts as an implementation
  only if it performs the function's documented core work for its
  principal inputs. Upstream semi-stubs (FIXME + a plausible-looking
  return for all substantive inputs), upstream stub bodies, and
  no-ops indistinguishable from the stub were rejected — mirroring
  them would shrink the baseline dishonestly.
- **12,323** are still winebuild stubs in upstream master itself.
- **1,381** do not appear in upstream master's spec for the DLL at
  all (legacy/undocumented/internal surface).

## Implemented: 203 baseline rows (107 x86-64 + 96 i386)

Backports of the upstream implementations, adapted to each shipped
vintage (Wine 8.0 x86-64 via
`tools/buildWine/patches/wine8-fd171-contracts.patch`; Wine 10.0
i386 via `wine10-fd171-contracts.patch`), staged hash-pinned into
both wine zips (`wine8-backports-x86_64/` via
`build-wine8-backports.sh`; `wine10-fd171-i386/` via the new
`tools/rootfs32/build-wine10-fd171.sh`, substituted by
`build-wine32-base.sh`; pins in
`tools/rootfs64/check_runtime_completeness.py` — checker: 0
failures).

Groups:

- **Config-manager family — 23 functions × 2 DLLs × 2 arches (92
  rows).** Implemented in setupapi's `devinst.c` on the vintage's own
  registry device model (Enum tree, Control\Class,
  Control\DeviceClasses), with cfgmgr32 spec entries as forwards:
  `CM_Enumerate_Classes_Ex`, `CM_Enumerate_Enumerators{A,W,ExA,ExW}`
  (the Ex forms use the corrected `_ExA/_ExW` spellings),
  `CM_Get_Class_Key_Name{A,W,ExA,ExW}`,
  `CM_Get_Device_ID_List_Ex{A,W}`, `CM_Get_Device_ID_List_Size_Ex{A,W}`,
  `CM_Get_Device_ID_Size_Ex`, `CM_Get_Device_Interface_List{A,W,ExA,ExW}`,
  `CM_Open_Class_Key{A,W,ExA,ExW}`, `CM_Open_DevNode_Key_Ex`.
  Upstream master's cfgmgr32 is a rewrite on a device/DEVPKEY model
  absent from both vintages, so contracts (CONFIGRET codes,
  validation order, size accounting) were taken from master and the
  data from the vintage's registry. Documented simplifications:
  failure-path buffers are fully zeroed (master leaves partial
  strings; return codes and the Size APIs are exact); relation
  filters (eject/removal/power/bus bits) match no device because the
  model has no relation data; "present" means present in the
  registry. One family member is blocked: `CM_Get_Parent_Ex` — the
  vintage records no parentage anywhere.
- **ntdll — 14 × 2 arches.** The splay-tree generic-table set
  (`RtlSplay`, `RtlDelete`, `RtlDeleteNoSplay`,
  `RtlInsertElementGenericTable`, `RtlDeleteElementGenericTable`,
  `RtlEnumerateGenericTable`, `RtlIsGenericTableEmpty`,
  `RtlRealPredecessor`, `RtlRealSuccessor`, `RtlSubtreePredecessor`,
  `RtlSubtreeSuccessor`) backported verbatim (types are identical in
  the vintage headers), plus the activation-context trio
  (`RtlActivateActivationContextUnsafeFast`,
  `RtlDeactivateActivationContextUnsafeFast`,
  `RtlQueryInformationActiveActivationContext`).
- **propsys — 6 x86-64, 1 i386.** `PropVariantToBSTR`,
  `PropVariantToUInt32WithDefault`, `PropVariantGetStringElem`,
  `InitPropVariantFromStringVector`, `PropVariantToVariant`,
  `VariantToPropVariant`. Only `PropVariantGetStringElem` was still
  a stub in Wine 10.0; the other five already work there.
- **pdh — 3 x86-64, 2 i386.** `PdhGetFormattedCounterArray{A,W}`
  (both arches) and `PdhVbGetDoubleCounterValue` (x86-64 only;
  already implemented in Wine 10.0).
- **combase — 7 × 2 arches.** HSTRING RPC marshaling
  (`HSTRING_UserMarshal/UserSize/UserFree/UserUnmarshal`),
  `RoGetErrorReportingFlags`, `RoFailFastWithErrorContext`,
  `RoFailFastWithErrorContextInternal2`. Three accepted with a
  note (below).
- **kernelbase/kernel32 — 7 rows × 2 arches.** `HeapSummary` (real
  HeapWalk accounting), `ReadConsoleInputEx{A,W}`, and kernel32's
  `RegisterWaitForInputIdle` (the pre-existing call sites now prefer
  a registered hook and keep the stock behaviour otherwise).
- **mfplat (x86-64) — 2.** `MFInitMediaTypeFromMPEG1VideoInfo`,
  `MFCreatePathFromURL`.
- **Single-function DLLs.** cryptext `CryptExtOpenCER/W`, d2d1
  `D2D1CreateDeviceContext`, hid `HidP_SetData`, mf
  `MFTranscodeGetAudioOutputAvailableTypes`, mscms
  `WcsGetCalibrationManagementState` (accepted with note), prntvpt
  five (three Thunk2 stream wrappers + `BindPTProviderThunk` /
  `UnbindPTProviderThunk` as aliases of the genuinely implemented
  `PTOpenProviderEx` / `PTCloseProvider`), sspicli
  `SspiMarshal/UnmarshalAuthIdentity`, vcomp family
  `omp_get_wtick` (6 tables × 2 arches; vcomp90's entry is a forward
  to vcomp, as its spec-only build requires), windows.networking
  `DllGetActivationFactory` (x86-64, accepted with note), wintypes
  `RoParseTypeName` (x86-64), wofutil `WofIsExternalFile` (x86-64,
  accepted with note).

Accepted with a note (the function reports the implementation's
actual mode/state, which is the truth for this environment and is
provably distinguishable from the winebuild stub):
`RoGetErrorReportingFlags` (reports USESETERRORINFO, this runtime's
actual error-reporting mode), `WcsGetCalibrationManagementState`
(no calibration management exists here; state is genuinely FALSE),
`WofIsExternalFile` (no WOF backing exists in the guest; files are
genuinely never externally backed), windows.networking
`DllGetActivationFactory` (the DLL registers no activatable classes;
REGDB_E_CLASSNOTREG is the correct answer for every class).

## Proof

- **Census:** baseline regenerated in this change: named stubs
  33,756 -> 33,553 — a drop of exactly the 203 implemented rows,
  verified name-by-name against the intended set, with zero new
  stubs and no other table touched. `dll_export_census.py --check`:
  exact match. The JS census unit test passes (4/4 with
  runtime-assets).
- **Guest contract fixtures:**
  `tools/guest-fixtures/fd171-contracts.c`, run by
  `web/tests/suite/browser/fd171-contracts64.test.mjs` and
  `fd171-contracts32.test.mjs`. Every group is exercised by calling
  the functions (generic-table insert/enumerate/delete ordering,
  CM enumeration + class-key open + ID-list size consistency,
  formatted counter array two-call protocol, HSTRING marshal
  round-trip, auth-identity marshal round-trip, HeapSummary
  accounting, and the rest). On the pre-fix runtime the fixture
  dies at the first stub call (Wine stub exception 0x80000100) and
  the RESULT line never prints. PROBE STATUS (2026-11-05, late):
  the box's probe slots were saturated all evening by the batch-9
  lanes finishing simultaneously plus a long proof build holding
  the slot system's build gate. The x86-64 RED run (against the
  pre-fix zips) acquired a slot and spawned the fixture, which
  produced no output before the runner cap killed the probe —
  consistent with death at the first stub call, but recorded here
  as inconclusive at guest level rather than claimed. Four
  subsequent GREEN attempts each waited the full 900 s probe-slot
  budget in the queue without acquiring a slot (pure contention;
  the waits and the queue state are preserved in
  `test-results/fd171/evidence/`). A retry loop was left running on
  the box (`/tmp/fd171-probe-loop.sh`, logs
  `/tmp/fd171-probe-green64.log` / `-green32.log`) to land both
  tests when a slot frees; the composition gate should collect
  those results (both tests are also part of the standard suite
  and will run at the batch gate regardless). The fixture itself
  compiles cleanly for both architectures (mingw, both arches),
  and the stub-vs-implemented distinction for exactly these 203
  rows is independently proven at the binary level by the census
  (above): the pre-fix binaries carry the validated winebuild
  stub body for each of the 203, the staged binaries carry real
  code, and no other export changed state.
- **Runtime completeness:** `check_runtime_completeness.py` passes
  with the new pin sets (source + shipped-zip member hashes);
  `bootstrap.py --check` verifies the new retained archive
  `runtime-assets-20261105-fd171` (13 files).
- **Dist:** `tools/bw64-build.sh` completes with the literal
  "Browser export verified" line; dist carries the staged zips.

`RoFailFastWithErrorContext(Internal2)` is the one implemented
group the guest fixture deliberately does not call: its contract is
to terminate the process. It is proven by source identity with
upstream (its core work is RaiseFailFastException) plus the census
reclassification; a Wine-10.0 header gap it exposed (no
`RaiseFailFastException` declaration in `winbase.h`, without which
the i386 build cannot link combase) is fixed inside the fd171
patch.

## What remains, and why (all 14,084 non-implemented entries)

Full per-function record:
`tools/conformance/dll_export_dispositions_fd171.json`. Summary:

- **12,303 — still stubs in upstream master.** No upstream
  implementation exists to backport and the correct behaviour
  cannot be lifted from an authoritative source; left rather than
  guessed, per the lane's rule. (Plus 57 whose upstream body is
  itself a stub, 9 upstream semi-stubs rejected, 4 upstream no-ops
  rejected — named in the record.)
- **1,381 — absent from upstream's spec entirely.** Legacy or
  undocumented surface (largest clusters: mapi32/mapistub legacy
  MAPI, rasapi32 legacy RNA, odbc32 CursorLib internals, wsnmp32,
  olecli32, cryptui dialog internals, shell32 internals).
- **270 — implemented upstream only inside a subsystem rewrite**
  that post-dates the vintage: the d3dx family (post-2023 d3dx
  core; master's texture entry points are thin wrappers over it),
  bluetooth (winebth radio stack), winscard (PC/SC handle layer +
  unix backend), ninput (interaction-context engine),
  uiautomationcore (rewritten UIA client), wpcap (rewritten unix
  dispatch). Each verified against a representative upstream body.
- **Named blocked (41).** `PSGetNameFromPropertyKey` (the
  IPropertyDescription subsystem returns E_NOTIMPL for everything
  in Wine 8.0), `CM_Get_Parent_Ex` (no parentage data exists),
  mfplat's video-format cluster and serialize family, imm32's IME
  trio, nsi's change-notification trio (driver ioctl absent),
  `HttpSendResponseEntityBody` (shared-struct ABI pair with stock
  http.sys), forwarders whose targets are absent/stub
  (d3d11/ncrypt/sechost), `RoGetAgileReference`,
  `MFCreateLegacyMediaBufferOnMFMediaBuffer`,
  `MFCreateSequencerSegmentOffset`, dbghelp's PDB-stream
  dependency, the d3dcompiler linker pair, `Wow64RaiseException`
  (untestable: no WoW64 guest can exist on a long-mode-only CPU
  emulator).
- **19 — implemented by the sibling FD-167 lane** on the same
  census base (bluetooth GATT set, winusb, `MFCreateDeviceSource`,
  `MFCreateMediaBufferWrapper`, `EvtRender`,
  `VariantCompare`); composition takes the union.
