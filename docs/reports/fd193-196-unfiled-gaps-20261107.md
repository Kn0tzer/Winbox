## FD-193 — vectored-read segment lengths (Medium) — CLOSED

Contract measured (`hostref-vec3.out`, `hostref-vec-arm32.out`,
`hostref-vec-arm32b.out`, `hostref-pv2-final.out`): any segment
whose length is negative read as the ABI's signed size (64-bit
≥ 2^63; 32-bit ≥ 2^31) answers `-EINVAL` before any byte moves,
wherever it sits in the array. The 32-bit side has NO sum check
({1 GiB, 1 GiB, 1} with sum 2^31+1 reads normally; {2 GiB−1,
2 GiB−1} reads). A successful transfer is capped at MAX_RW_COUNT
= 0x7ffff000 = 2147479552 bytes exactly (measured from /dev/zero
with one 2^31 segment and with two segments summing to 2^31).
Boundary the entry states and the fix does not reproduce: the
host also answers `-EFAULT` for segment ranges beyond the address
space ({2^62, 2^62}; {8, SSIZE_MAX}); the emulator's flat guest
memory has no equivalent range validation.

Fix: the per-segment signed check in all four validation paths
(64-bit `sys_readv64` / `sys_preadv64`, 32-bit `KProcess::readv` /
`KProcess::preadv`), placed after the iovec-array check and ahead
of the preadv2 flags check; the 0x7ffff000 cap in all four walks,
with the 32-bit cap riding the shared `KObject::readv` walk (its
U32 running total can no longer wrap).

## FD-194 — positioned reads (and writes) on unseekable objects (Medium) — CLOSED

Contract measured (`hostref-pv2-final.out`, authoritative; both
widths identical on every row): a missing descriptor answers
`-EBADF` first; an unseekable object then answers `-ESPIPE`
ahead of the iovcnt range, the iovec array and the preadv2 flags
answers; `pread64` answers ESPIPE ahead of its negative-offset
`-EINVAL`; `preadv`'s own negative offset answers `-EINVAL`
ahead of ESPIPE; `preadv2` offset −2 answers `-EINVAL`, offset
−1 is the file-position mode and READS from a pipe (flags still
validated first — a bad flag answers `-EOPNOTSUPP` ahead of the
read). Pipe bytes are never consumed by a refused positioned
read. The unfixed 64-bit side did the worst thing available: its
positioned read ignored the position and silently consumed the
pipe's bytes.

Fix: the seekability answer is hoisted to immediately after
descriptor resolution in `sys_preadv64`, `sys_pread64Impl`,
`KProcess::preadv` and `KProcess::pread64`, with the
file-position mode exempted and delegating to the plain vectored
read after full validation. One refinement the checking queue
forced: the delegation applies to unseekable objects only — a
real file keeps the offset-explicit walk (whose post-walk seek
advances the tracked position), because the 64-bit sequential
read path does not maintain that position. The queue's full
x64 suite caught the unconditional delegation returning 0 on a
file at a live position (FD-80's preadv2 offset -1 cases);
the same split was applied to the write twin, and the
position-advance the walk performs was restored where the
first version of this fix had removed it as dead. The 32-bit
model layer's vectored calls are position-tracked internally,
so its delegation stands for all objects. The positioned-WRITE
twins are corrected in the same pass (measured in
`hostref-pwtwins64.out`, `hostref-pwtwins32.out`,
`hostref-pwt2-64.out`, `hostref-pwt2-32.out`): `sys_pwritev64` /
`KProcess::pwritev` hoist `-ESPIPE` the same way and delegate
their file-position mode to the plain vectored write;
`sys_pwrite64` gains the answer after its descriptor check;
32-bit `KProcess::pread64` / `pwrite64` move their non-file
answer from `-EINVAL` to `-ESPIPE` (sockets already answered
it; ftruncate64 / fchdir keep theirs).

Two measured corners are stated boundaries, not fixed: (1)
`pwritev2` with RWF_APPEND and the file-position mode on a pipe —
the host's own ABIs disagree (native answers `-EBADF`, compat
writes), so that combination keeps the walk's current answer;
(2) `pwrite64` with a negative offset on a pipe — the native
path answers `-EINVAL` ahead of `-ESPIPE`, the compat path
answers `-ESPIPE`; each core follows its own ABI.

Method note: the first pwritev2 probe hung on a blocking drain
read when no write landed; the final probe drains non-blocking.
An early measurement script for the write twins also invoked the
compat `pwritev` under i386's number (334) instead of ARM EABI's
(362) and produced garbage rows; discarded, re-measured.

## FD-195 — 32-bit `linkat` missing (Medium) — CLOSED

Slot 303 was `nullptr`: every 32-bit `linkat` answered
`-ENOSYS`. Contract measured (`hostref-linkat64.out`,
`hostref-linkat32.out`; identical on every row): flags outside
`AT_SYMLINK_FOLLOW | AT_EMPTY_PATH` answer `-EINVAL` ahead of
even the null-path fault; null path `-EFAULT`; empty path
`-ENOENT`; bad dirfd `-EBADF`; file-as-dirfd `-ENOTDIR`; missing
source `-ENOENT`; existing target `-EEXIST`; directory source
`-EPERM`; dirfd-relative resolution works on both sides;
`AT_EMPTY_PATH` + empty old path + file descriptor links the
file, + pipe descriptor answers `-EXDEV`; without
`AT_SYMLINK_FOLLOW` the link names the symlink itself, with it
the target. Fix: `KProcess::linkat` (each side resolved through
the established dirfd helper, delegating to `KProcess::link`;
the descriptor form returns `-EXDEV` for non-file objects) and
a dispatcher whose flags check precedes FD-132's null-path
check, wired at slot 303. The 64-bit dispatcher's own linkat
(dirfds ignored, descriptor form at its current answer) is
named in the entry as a boundary outside the closing terms.

## FD-196 — Vulkan trap traffic feeds no metrics counter (Low) — CLOSED

FD-63's entry named this boundary: the emission gate counted
Vulkan activity only at frame completion, so a guest trapping
Vulkan calls forever without presenting emitted nothing. Fix: a
per-trap hook, `bw64_metrics_vk_trap(int arch)`, called from
`VkProfTrapTimer`'s destructor ahead of the timing gate in both
bridges; it flushes any due snapshot before accounting (FD-63's
flush-before-accounting rule), increments the existing 64-bit
trap counter (the one the snapshot prints) or a new gate-only
32-bit counter that is drained on window reset and never
printed; `bw64_metrics_vk_frame` no longer adds the frame's trap
count a second time. The JSON schema is unchanged and the
committed metrics fixture is byte-identical — the official
regeneration differs only in one clock-jitter field
(`frameMs` 600.14 → 600.12) and was not shipped.

RED statement, plainly: on the base there is no per-trap API at
all (`bw64_metrics_vk_frame` is the only Vulkan input to the
registry), so the extended selftest cannot link against base
headers; the fix's proof is the extended selftest passing on the
fixed tree (trap-only windows emit on both arches; the first
snapshot reports `"frames":0` with the trap count present) plus
the fixture byte-check above.

## FD-197 and FD-198 — filed open by this lane

FD-197 (Low): the vectored-WRITE family shares FD-193's
unguarded shape (found by inspection while fixing FD-193). The
host contract is expected to mirror the read side because the
kernel's vector import is shared, but this lane did not measure
the write side's length handling — the entry stays open on that
honesty; its closing terms start with the raw-syscall matrix.

FD-198 (Low): `sys_read64` opens with `if (fd == 0) return 0;` —
descriptor 0 answers end-of-file whatever it names. Found while
staging this lane's x64 fixtures: the data file landed on
handle 0, `pread64` read it correctly, `readv` answered 0 with
the position at 0. The lane's x64 test now stages a throwaway
descriptor first. Not fixed here.
