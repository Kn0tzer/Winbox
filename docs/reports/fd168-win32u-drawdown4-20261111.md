## What the slice implements (when built)

Three x86-64 win32u placeholders become real implementations in the
Wine 8 backports build, via
`tools/buildWine/patches/wine8-win32u-fd168-slice4.patch`
(wired into `tools/rootfs64/build-wine8-backports.sh`'s PATCHES list
after the slice-3 patch):

- **NtUserGetTopLevelWindow** — spec stub to `@ stdcall -syscall`,
  syscall-table entry, body in `window.c` forwarding to `NtUserGetAncestor( hwnd, GA_ROOT )`. The
  top-level window of a window is its root ancestor: itself when
  already top-level, else the ancestor just below the desktop, which
  is exactly the walk `NtUserGetAncestor` computes for `GA_ROOT`
  (the same identity slice 2 used for `NtUserIsTopLevelWindow`).
- **NtGdiGetTextExtent** — spec stub to `@ stdcall`, body in
  `wrappers.c` calling `NtGdiGetTextExtentExW( hdc, str, count, 0,
  NULL, NULL, size, flags )`. ReactOS's own implementation is this
  exact call, and its comment records the flag values: 0 is the
  `GetTextExtentPoint32W` form, 1 the `GetTextExtentPointI`
  (glyph-index) form. `max_ext` is unused when `nfit` is NULL, as
  the tree's own `NtGdiGetTextExtentExW` body shows (the limit is
  only consulted when `nfit` is non-NULL) — and gdi32's
  `GetTextExtentPoint32W` already makes exactly this call.
- **NtGdiGetGlyphIndicesWInternal** — spec stub to `@ stdcall`,
  body in `wrappers.c` forwarding to the existing
  `NtGdiGetGlyphIndicesW` with `flags = iMode`, `bSubset` ignored.
  ReactOS's public `NtGdiGetGlyphIndicesW` forwards to its Internal
  with `bSubset = FALSE`, and ReactOS's font engine carries
  `bSubset` as an unimplemented FIXME, so the flag has no observable
  effect on either side. The count validation is ReactOS's
  win32k-side check, kept verbatim (`count < 0` and `count == 0`
  with real pointers answer `GDI_ERROR`; the all-NULL probe
  forwards NULLs to the sibling). The tree's unix
  `font_GetGlyphIndices` never dereferences the string when
  `count == 0` (its loop does not run), so the probe cannot fault
  there; the fixture still guards the probe call and asserts
  agreement with the sibling called the same way.

Expected census effect when the resume builds it: x86-64 win32u
stubs 903 -> 900; i386 unchanged at 1,111; FD-168 total
2,014 -> 2,011; only `x64/win32u.dll` changed across all 1,171
tables. The patch is +48/−3 across 6 files (spec, syscall table,
`window.c`, `wrappers.c`, `include/ntgdi.h`, `include/ntuser.h`).

## How the candidates were found (the sweep)

The slice-3 record closed with "no upstream-portable candidates
remain for a further slice of this shape". This lane re-verified
that claim from the primary sources instead of trusting it, and
found it true on the upstream side but incomplete on the
in-tree-composition side:

- **Upstream Wine 10.0's `win32u.spec` (fetched, parsed in full,
  1,543 entries): exactly 29 of the 903 remaining x64 stubs are
  real there — 23 `NtGdiDdDDI*` names and 6 others
  (`NtUserEnableMouseInPointer`, `NtUserGetPointerInfoList`,
  `NtUserIsMouseInPointerEnabled`, `NtUserNotifyIMEStatus`,
  `NtUserRegisterTouchPadCapable`, `NtUserSwitchDesktop`) — and
  every one of the 29 is already dispositioned in the FD-168
  register entry (D3DKMT layer, FIXME semi-stubs,
  machinery-blocked). The only name absent from Wine 10's spec
  entirely is the misspelled
  `NtUserSendInteracsetiveControlHapticsReport`, also already
  dispositioned. The other 873 are stubs in Wine 10 too. So no
  upstream port is available for any of the 903. (An earlier
  parse of the same file briefly reported 0 real names; that was
  a regex bug dropping every `-syscall` line — caught by
  grepping the file directly and re-parsing with the flags
  handled. The 29-name figure is the corrected one.)
- **In-tree callers: none.** A whole-word sweep of Wine 8.0's
  `dlls/win32u`, `dlls/user32`, and `dlls/gdi32` sources finds
  ZERO references to any of the 903 stub names (outside the spec
  itself). No body exists to wire up, and no in-tree caller
  exists to complete. The only route left is composition from
  related machinery under different names, the slices 2-3 shape.
- **Compositions verified:** the three in this patch are the
  ones whose semantics are fully determined by machinery the
  tree already has AND pinned by a second source (ReactOS's
  implementation for the two GDI names; the tree's own
  `NtUserGetAncestor` body plus slice 2's established GA_ROOT
  identity for the user name). Each was checked against the
  actual Wine 8 bodies it composes (`NtGdiGetTextExtentExW`'s
  `max_ext` handling, `font_GetGlyphIndices`' count-0 loop,
  `NtUserGetAncestor`'s GA_ROOT walk, the syscall-table/spec
  order match).

## Candidates examined and refused (do not re-open without new evidence)

- `NtUserGetMenuIndex` — contract contradiction: the name says
  it returns an index, but ReactOS's implementation returns the
  matching item's `wID` (or `0xFFFFFFFF` when not found). With
  the two signals disagreeing, the return value cannot be
  pinned; refused as unpinnable, same class as slice 2's
  `NtUserGetDpiForCurrentProcess` refusal.
- `NtGdiGetDCforBitmap` — ReactOS returns the surface object's
  own stored `hdc` (a surface-owned handle of unclear lifetime);
  a Wine composition would have to CREATE a caller-owned DC
  (compatible DC + select the bitmap), which is a different
  ownership contract that cannot be proven equivalent. Refused.
- `NtGdiGetDeviceCapsAll` — the `DEVCAPS` struct layout is in
  neither Wine 8's headers nor the ReactOS headers fetched
  (`sdk/include/psdk/ntgdi.h`, `win32ss/include/ntuser.h`);
  without the authoritative layout the fill cannot be written.
  Refused as unpinnable (a composition from `NtGdiGetDeviceCaps`
  per index would be the shape, once the layout is sourced).
- The slice-2 refusal list still stands and was not re-litigated:
  the DPI point transforms, `NtUserGetDpiForCurrentProcess`,
  the ShutdownBlockReason trio, `NtUserGetGuiResources`,
  `NtUserSBGetParms`, `NtUserQuerySendMessage`, the ICM family,
  `NtUserGetComboBoxInfo`/`NtUserGetListBoxInfo`,
  `NtGdiEnumObjects`, the `NtUserCallHwnd*` variants, the
  Eng*/FONTOBJ/STROBJ display-driver DDI surface, the eight
  upstream FIXME semi-stubs, and the six machinery-blocked names.
  The 215-name compositor/input-compositor cluster, the
  `NtGdiDdDDI*` surface, and the pointer/touch/IME/DPI long
  tails remain dispositioned per the register entry; this lane
  found no in-tree machinery that determines any of their
  semantics.
