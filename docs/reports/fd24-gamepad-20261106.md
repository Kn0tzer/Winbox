## The end state this lane worked to

A game controller connected to the computer running the browser is
visible to Windows programs in the emulator through the standard
controller interfaces: the program can detect it, read buttons and
sticks, and see values change — proven by a purpose-built test
program driven by a simulated controller in the test harness.

## What is now true, link by link (each measured)

1. **Host feed.** The SDL layer opens the first host controller and
   feeds the kernel gamepad entry points
   (`platform/sdl/knativeinputSDL.cpp`): SDL_GameController when the
   device classifies, raw joystick in the W3C standard layout
   otherwise (raw-path triggers degrade to digital 0/255 — the raw
   API carries no analog trigger values). Full-state sync on open,
   neutral state on removal, per-direction D-pad composed onto the
   hat axes, and the duplicate raw-joystick event stream for an
   already-open game controller is consumed so nothing double-feeds.
   The gamepad/joystick SDL subsystems are enabled with video
   (`platform/sdl/knativesystem.cpp`). In the browser build this path
   is fed by the browser Gamepad API through Emscripten's SDL.
   Measured live: the browser-build session log records
   `Gamepad feed: controller 'Standard Gamepad' opened (instance 0)`
   for the harness's simulated pad.
2. **Kernel device.** Pre-existing (round 3B, `2882a52a3`):
   `/dev/input/event5`, 15 buttons, 6 axes, Xbox-360 identity
   (045e:028e), proven by the native `testDevInputJoystick`.
3. **Guest discovery — sysfs.** The guest had no `/sys` input class
   at all (measured: `opendir /sys/class/input` → ENOENT, libudev
   enumeration 0, while a direct open of the device node worked).
   `source/kernel/sys/sysinput.cpp` (new) now publishes
   `/sys/class/input/event5` and its parent input device with the
   id and capability files a real kernel publishes, in the shape of
   the existing framebuffer sysfs pattern.
4. **Guest discovery — statfs (new defect FD-172, fixed).** With
   sysfs present, libudev still rejected every device. Reading the
   staged guest libudev's own code showed its device verification
   requires the sysfs path to statfs as SYSFS_MAGIC; the emulator
   answered one flat filesystem type everywhere (EXT3 on the 32-bit
   layer, tmpfs on the 64-bit layer). All four statfs entry points
   now report SYSFS_MAGIC under `/sys` and PROC_SUPER_MAGIC under
   `/proc`, previous answers elsewhere. Measured after the fix: the
   guest probe enumerates the gamepad through libudev (device
   creation from its sysfs path succeeds, subsystem "input"),
   where the unmodified build enumerated nothing. Pinned by native
   tests on both widths (`testStatfsMagicByMount32Calls`,
   `testStatfsMagicByMount64Syscalls`).
5. **Guest discovery — udev data.** Reading the staged winebus
   library's own code showed device classification is by udev
   properties (`ID_INPUT_JOYSTICK` and family), which on a real
   system come from the udev database. No udev daemon runs in the
   guest, so `sysinput.cpp` also synthesises the database entry a
   real system would hold for this device (its joystick verdict for
   the declared capability bits). This link follows the library's
   measured contract; it could not be separately re-measured on the
   final build because the chain's observable end stops at the
   driver boundary below (the diagnostic probe's output window
   expired under load on its last run).

## Where the chain stops today (measured, filed)

The witness (XInput + DirectInput) still reports no controller, and
the reason is no longer anywhere in the emulator's controller path:

- **FD-173 — kernel-mode Wine drivers fail to initialise in the
  emulator.** On the 32-bit side everything is registered and the
  PlugPlay service runs (guest probe: state 4), the WineBus service
  exists but stopped (state 1), and starting it fails with error
  1114 (DLL initialisation failed). The same failure hits every
  kernel driver: session logs record ZwLoadDriver c0000142 for
  MountMgr, nsiproxy, NDIS and wineusb — including in preserved
  logs from unmodified builds (other lanes' suite consoles), so
  the condition predates this lane and is independent of its
  changes.
- **FD-174 — the shipped 64-bit prefix has no PlugPlay
  registration.** Guest probe on the 64-bit side: OpenService
  answers error 1060 for PlugPlay, WineBus and WineUsb, and the
  root device enumeration is empty. `prefix64.zip`'s system.reg
  contains no PlugPlay or WineBus entries; `prefix32.zip` carries
  them.

FD-24 therefore stays open on FD-173 and FD-174. The witness test
(`web/tests/suite/browser/input-gamepad.test.mjs`, currently red at
the slot-0 connect wait for exactly these reasons, and marked so in
its header) is the proof vehicle the moment either blocker lands:
it asserts XInput connect/caps/state changes (buttons, triggers,
sticks, D-pad) and DirectInput enumeration/state against the
simulated pad on both architectures.

## Carried limits, stated plainly

- One controller only: the kernel models a single pad; XInput
  slots 1–3 truthfully report "not connected".
- The legacy WinMM joystick interface is not carried: there is no
  `/dev/input/js0` (the kernel lane's recorded decision — no
  current consumer uses the legacy js driver).
- Force feedback is not carried: the device advertises none.
- A real browser only exposes a physical pad to the page after the
  user presses a button on it — a browser platform rule, not an
  emulator gap.
