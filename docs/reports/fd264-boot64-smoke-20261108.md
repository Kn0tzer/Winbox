# FD-264 — the 64-bit boot smoke test never sees its payload run

## The defect

`boot64-smoke` failed five times in a row across the batch-11 and batch-12
gates (three in batch 11, two in batch 12, including focused re-runs in
verified quiet windows). The first two milestones were always met (the guest
loader's execve, then user32 loading) but the third — the booted
`cmd /c echo vkboot` producing its output line — never arrived inside its
240 s wait. The guest was alive and working through device enumeration at
each kill, with no fault in the stream, and every other 64-bit boot in the
suite passed on the same guest setup. The test passed the batch-10 gate.

## Investigation

Static comparison of the preserved batch-10 (passing) and batch-12 (failing)
consoles, with a wall-time timeline built from the consoles' own
`bw64: METRICS` heartbeats (one per ~0.5 s):

| milestone (wall time from first heartbeat) | batch 10 | batch 12 | delta |
|---|---|---|---|
| sys_execve64 | t+14.4 s | t+15.1 s | +0.7 s |
| user32.dll | t+52.8 s | t+56.4 s | +3.6 s |
| create_winstation (WinSta0) | t+118.5 s | t+198.2 s | +79.7 s |
| wineboot exit | t+141.6 s | t+201.7 s | +60.1 s |
| second cmd execve (the one that prints) | t+176.6 s | t+262.8 s | +86.2 s |
| `log: vkboot` | t+212.7 s | never (killed t+298 s) | — |

The batch-12 console also carries 5 distinct driver installs (10 `InfPath`
lines counting the request/echo pairs) that batch 10 has none of. The
second cmd's main thread, at the kill, was still doing startup work (MUI /
timezone registry reads), never reaching the console write — but the
installs were spread through the whole run, progressing, not stuck on one.

## Decisive experiment: two live runs against the shipped batch-12 build

A live probe (`test-results/fd264-proof/live-boot64-probe.mjs`, probe slot
held, quiet box) ran the test's exact parameters against the live site
(batch 12, wasm `62f6123e…`), twice: first a discovery run with the vkboot
wait extended to 600 s, then a proof run with the fixed 360 s wait. Both
runs' consoles are preserved
(`test-results/fd264-proof/live-boot64/live-g1-discovery/console.txt` and
`live-g1/console.txt`).

What they show:

- **The guest is not stuck.** In both runs the booted shell ran `echo
  vkboot`, wrote `vkboot\r\n` to its console (two
  `IOCTL_CONDRV_WRITE_CONSOLE` calls, both answered `NOT_SUPPORTED` — the
  same answer batch 10 got), and exited status 0. The echo output
  arrived as `log: vkboot` at t=362.0 s (discovery) and t=357.6 s (proof).
- **The boot is slow, and the slowness is after user32.** user32 at
  65.8 s / 64.4 s; the echo at user32+296.2 s / user32+293.2 s. Batch 10
  needed user32+159.9 s. The second cmd starts ~123 s later than batch 10
  (t+300 s vs t+177 s) and takes ~62 s to print (vs 36 s).
- **The cause is the driver installation batch 11 introduced.** Every
  fresh 64-bit boot now installs the HID/XInput drivers — 9 installs
  (winehid ×4, input ×4, winexinput ×1) spread t+150 s → t+422 s — that
  batch 10 never did: the driver INFs shipped (FD-188), the PnP sections
  were registered (FD-189), and WineBus/udev enumeration went live
  (FD-195). The installs run concurrently with the boot (the last one
  lands after the echo prints), so they do not gate the print directly;
  the whole boot is slower, and the batch-12 desktop boots show the same
  shift (~200–300 s vs batch 10's ~120–195 s). The test's 240 s vkboot
  wait expired 56–64 s before the echo landed in both runs.
- **The 32-bit twin is unaffected** — `boot32-vkboot` passes in ~57 s in
  the same suite (it does 5 installs, not 9, on the faster 32-bit path).

## The fix

`web/tests/suite/browser/boot64-smoke.test.mjs`: the vkboot wait
240 s → 360 s, with a comment naming the cause (above). One line of
behavior change; the build is untouched (test-only fix, wasm identical).
360 s covers the measured 293–296 s with ~64 s of margin.

## Proof

The test's own sequential waits and regexes were replayed against both
saved live consoles by `test-results/fd264-proof/replay-boot64-waits.py`
(result in `test-results/fd264-proof/replay-result.txt`, exit 0):

- Discovery run: execve 21.7 s, user32 65.8 s, **vkboot 362.0 s
  (user32+296.2 s)**, winstation 385.5 s (vkboot+23.5 s) — PASS.
- Proof run: execve 20.5 s, user32 64.4 s, **vkboot 357.6 s
  (user32+293.2 s)**, winstation 382.1 s (vkboot+24.5 s) — PASS.

Checking-service pipeline: NOT RUN — blocked on disk. At submission time
the box had 899 MB free; the pipeline's `prepare-workspace` step copies the
whole source tree (~929 MB, checks/src including its 499 MB .git) before
any check runs, so a submission would fail with ENOSPC and risk filling the
disk to zero. The queue was idle (no wp_* job containers) and the lane did
not submit. What was verified instead, on this branch, locally: the citation
audit passes (352 rows, 0 drift, exit 0) and the JS unit suite passes
353/1 with the single failure the known bare-checkout artifact
(`provenance-artifacts`, needs a built dist/) — the standard shape's
family. The native suites, js-legacy, and run-native were not run: they
need a build, which the same disk floor forbids. The queue run is owed to
the batch-13 composition (or whenever disk allows).

## Verification-process note (honest)

The first live probe reported `VKBOOT-NEVER` — wrong. Its matcher tested
the test's regex (`^log: vkboot…`) against console lines that carry the
probe's own `[362.0s] ` elapsed prefix, so the anchor never matched even
though the echo line was in the capture. The saved console, read directly,
shows the line at t=362.0 s. The replay script strips only the elapsed
bracket (keeping `log: `) and is the verification that counts; the probe
file was corrected the same way. Do not cite the first probe's
`VKBOOT-NEVER` summary — it is a matcher artifact, not a guest result.

## What this fix does not do

- It does not make the boot faster. A bare 64-bit `cmd` taking ~360 s to
  print is a speed problem, and speed is FD-26's territory (open). This
  guard now measures the boot the project actually ships instead of the
  boot batch 10 shipped.
- The 360 s wait has ~64 s of margin over the two measured runs. If a
  future gate run under heavier load exceeds it, that is signal the boot
  got slower again, not test noise — revisit the wait then, don't just
  raise it.
- Open follow-up, not this fix: the 64-bit boot installs 9 drivers where
  the 32-bit boot installs 5. Whether the emulator's synthesized udev
  surface presents HID devices that should not be there (phantom devices
  causing redundant installs) belongs to the FD-195 area.
