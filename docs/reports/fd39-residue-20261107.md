# FD-39 -- the effect-only residue is proven unfixable in the shipped backends (2026-11-07)

Branch `lane-fd39-residue`, off integ tip `faf95d26c`. Fix commit
`8258111c6` (the CLAMP_TO_BORDER correction below). Register: FD-39
CLOSED as proven unfixable -- see CL-137 (lane-local number;
settles at the next composition). FD-45 (the vector-entry-point /
query surface) is a separate entry and is untouched.

## The question

FD-39's 2026-10-31 fix left an effect-only residue: LOD bias,
border color, texture swizzle and depth-texture mode are stored,
validated and queryable on both GL routes, but no backend models
their *sampling effects*. The entry's own closing condition was
"sampler/shader support in a backend". This lane set out to
either add that support or prove it cannot exist in the backends
the product ships. Result: one real correction (below), and a
proof that the four effects cannot be expressed as
texture/sampler state in either shipped backend.

## Correction found on the way: CLAMP_TO_BORDER never reached a real sampler

The 2026-10-31 record claims the CLAMP_TO_BORDER wrap "reaches
the sampler as WebGPU clamp-to-border". It does not: WebGPU has
no such address mode. `GPUAddressMode` in the project's vendored
types (`node_modules/@webgpu/types/dist/index.d.ts`) is exactly
`'clamp-to-edge' | 'repeat' | 'mirror-repeat'`, so the string the
backend wrote into `createSampler` is a value a real GPUDevice
rejects. Only the recording device used by the unit tests ever
accepted it -- its `createSampler` returns the descriptor
unexamined (`web/tests/suite/fixtures/webgpu-validation-device.mjs`).

Fixed in `8258111c6`: the WebGPU backend now decodes
CLAMP_TO_BORDER to `clamp-to-edge` -- the same disposition the
Vulkan tier documents for the same mode -- the raw mode stays in
the params map, and the approximation is logged once per backend
instance. Proof: `gl-fd39-texparams` updated to assert the decode
and the retained raw mode; red on the old mapping
(`test-results/fd39-residue/red-texparams.log`: expected
'clamp-to-edge', actual 'clamp-to-border'), green on the fix
(`green-texparams.log`); the neighbouring GL/Vulkan sampler
tests pass 21/21 (`neighbours.log`).

## The evidence matrix

The two shipped GL routes are the WebGPU backend
(`web/gl-webgpu.mjs`) -- the default: `wine64-launcher.js` sets
`BW64_GL_BACKEND=webgpu` unless a parameter says otherwise --
and the C++ bridge route (`source/opengl/gl64bridge.cpp`), whose
host in the browser build is WebGL2 (the emscripten makefile
pins `-sMAX_WEBGL_VERSION=2`), reached through Emscripten 6.0.9.

**WebGPU route.** `GPUSamplerDescriptor` in the vendored types
carries exactly: addressModeU/V/W, magFilter, minFilter,
mipmapFilter, lodMinClamp, lodMaxClamp, compare, maxAnisotropy.
No borderColor, no LOD bias, no swizzle.
`GPUTextureViewDescriptor` adds format / dimension / aspect /
level / layer selection -- and a `swizzle` string that its own
documentation gates on the optional `texture-component-swizzle`
device feature, which this backend never requests
(`gl-webgpu.mjs` calls `requestDevice()` with no
`requiredFeatures`) and nothing in the tree probes for. The
project's Vulkan tier states the same limits in shipped code:
`vk64bridge.cpp` sets `maxSamplerLodBias = 0.0f` with the
comment "WebGPU has no sampler LOD bias; advertise only what is
honoured", and `vk-sampler-rejection.test.mjs` records "WebGPU
has no border addressing".

**Legacy route.** The ES 3.0 header Emscripten ships
(`GLES3/gl3.h` -- the API WebGL2 implements) defines none of
`TEXTURE_LOD_BIAS`, `TEXTURE_BORDER_COLOR`,
`DEPTH_TEXTURE_MODE` or `CLAMP_TO_BORDER` (token census: 0
each), so no layer above the host can express those as state.
Emscripten's own library forwards `glTexParameteri` to the
context verbatim (`libwebgl.js`: `GLctx.texParameteri(target,
pname, param)`), so the one member of the set ES 3.0 does
define -- `TEXTURE_SWIZZLE_R` (census: 1) -- would reach the
host if the bridge forwarded it. That single cell is addressed
separately below. (The ES 3.2 header does carry border tokens,
but WebGL2 is ES 3.0 and the build pins it; the census above is
the 3.0 header.)

**The shader-rewrite boundary.** The remaining theoretical
route for LOD bias, swizzle and depth-texture mode on the
WebGPU backend is rewriting individual sampling expressions in
the translated WGSL (bias is a per-call argument there --
`textureSampleBias` -- not sampler state; swizzle and the
depth modes are post-sample reshaping). The GL backend does
not author those calls: guest GLSL is translated wholesale
(`toWGSL` in `web/gl-webgpu.mjs`), and the per-texture values
would have to be plumbed into generated pipelines as new
state. That is the "sampler/shader support in a backend" the
entry named -- a new shader-engine feature, not a disposition
available to this lane. The Vulkan tier's border-colour
rewrite (`rewriteBorderSamplersWGSL` in `web/wgsl-utils.mjs`,
applied by `web/vkwebgpu.mjs` to its own pipelines) is the
prior art such a feature would follow; it exists only for
that tier's sampled-image ops, with gather and cube sampling
explicitly approximated there.

## The one expressible cell, and why it was not taken

Texture swizzle on the legacy route is expressible end to end
(ES 3.0 defines the pnames; Emscripten forwards them). It was
not implemented, for two recorded reasons: (1) it cannot close
this entry -- the default WebGPU route still could not express
the effect, so the residue would remain; (2) it would make the
same guest program render differently depending on which
backend its session happened to land on, while today both
routes agree that the set is honest state without sampling
effects. If the legacy route ever becomes the primary GL
route, or a route-parity decision is taken, this cell is the
identified starting point.

## Disposition

FD-39 is closed as **proven unfixable within the shipped
backends**: the four sampling effects are texture/sampler
state in GL, and neither backend's state model contains them
(the swizzle escape hatches -- an unrequested optional WebGPU
feature, and the fallback route's native pnames -- are
recorded above). The 2026-10-31 disposition stands unchanged
and is now final: the values are set, validated and queryable
on both routes, with no sampling effect, and sessions render
the same on either route. Revisit only if a backend gains the
state (a requested `texture-component-swizzle` feature would
cover swizzle on the WebGPU route) or the GL shader-tier
feature described above is undertaken.
