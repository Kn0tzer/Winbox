## The defect

The 32-bit staged system files carried the same two desktop-initialization
impatience defects as the 64-bit set (FD-01): a 10-second
`NtUserWaitForInputIdle` fuse in win32u's `get_desktop_window`, and a
check-once-then-give-up latch in `load_desktop_driver`. Under the emulator's
slow cold start, the first check regularly ran before the winstation atom was
published, win32u latched the failure, and the desktop never came up
("The explorer process failed to start"). The 32-bit payload has a different
provenance from the 64-bit one — a pinned WineHQ Wine 10.0 Debian package,
not a from-source build — so the FD-01 backport pipeline could not reach it;
this lane built the 32-bit route.

## The fix (in-pipeline, survives rebuilds)

- `tools/buildWine/patches/wine10-win32u-desktop-wait.patch` — the twin of the
  Wine 8 patch, adapted to Wine 10.0's actual source (verified line-by-line
  against the pristine 10.0 tarball): the fuse becomes 300 000 ms; the driver
  probe retries every 500 ms for up to ~300 s, preserving Wine 10's two
  semantic drifts (the null-GUID fallback on a failed atom query, and the
  `!KeUserModeCallback` return convention). Definitive answers still return
  immediately — only the not-yet-published case waits.
- `tools/rootfs32/build-wine10-win32u.sh` — builds ONLY `win32u.so` from the
  pinned Wine 10.0 tarball (sha256-pinned) with the patch applied, in a pinned
  i386 sysroot (9 Debian bookworm debs, sha256-pinned), mirroring the stock
  module's feature configuration — freetype and fontconfig KEPT (the stock
  module dlopens both at runtime and the guest ships both; a `--without`
  build would have silently stripped guest font rendering). Fail-closed
  checks: config markers, no `__isoc23_*` symbols (the base pipeline's known
  glibc trap), ntdll linkage.
- `tools/rootfs32/wine10-backports-i386/win32u.so` — the built module,
  committed: 1,497,428 bytes, sha256
  `b2d9d135150b42a4785775451d5c296677bfb3d0dfaa6c57654a710c1dea7760`.
  Verification against the stock module it replaces (sha256 `ca5dd9c5…`):
  identical defined+undefined symbol sets (449 defined) versus a same-tree
  stock control build; identical DT_NEEDED; no glibc version above 2.35;
  disassembly shows the 300 000 ms constant and the 500 ms / ~600-attempt
  retry loop calling `NtDelayExecution` inside `load_desktop_driver`.
- `tools/rootfs32/build-wine32-base.sh` substitutes the backport (hash-pinned,
  fail-closed) immediately after the pinned deb is extracted, so all four
  shipped copies of the module inherit it (the base tree's own re-layout
  produces the other three). The patchelf injection set is unchanged
  (win32u needs no shim — verified: no `__isoc23_*` references).
- `tools/rootfs32/regen-wine32-zip.sh` step [4/5] now sanctions exactly the
  four win32u members differing from the previously shipped zip, each required
  to hash-match the committed backport; every other member must remain
  byte-identical (1926 members checked).
- `tools/browser/check_runtime_completeness.py` gained the standing pin test
  `t_wine10_backport32_source_and_zip` (source module + all four shipped
  copies), registered in the suite list.
- Pins/manifest: `tools/browser/runtime-assets.json` wine32 row and

## Measurement (hardened rules, fresh state, one boot per run, 900 s window)

Driver: `tools/browser/startup-measurement.mjs --arch=x86`, certification =
plausible deskpin handle AND ≥5 accepted X11 connections AND explorer.exe
actually opened (the merged hardened observer, unmodified). Three arms,
interleaved (B0, B1, F rotating), each boot a fresh profile, no restarts,
no outside rescue. Evidence: `test-results/fd02-20261031/` (per-boot
boot.json + console.log, summary, run log).

| Arm | Boots | Certified | Median ready | Mean load (1 m) |
|---|---|---|---|---|
| B0 — today's shipped state (unmodified integ code + stock wine32.zip) | 3 | **0/3** | — (63 s to a desktop the rules cannot certify) | 8.1 |
| B1 — FD-48 signal fix only + stock wine32.zip | 3 | **3/3** | 66 s | 2.2 |
| F — signal fix + this lane's fixed wine32.zip | 5 | **5/5** | 74 s | 6.4 |

Reading, stated plainly:

- **The fixed arm meets the end state**: 5/5 first-attempt cold starts
  certified under the unweakened hardened rules, fresh state every boot,
  zero "explorer process failed" lines, zero restarts — under the heaviest
  average load of the three arms.
- **The B0 zero is two stacked defects, not one.** All three B0 boots were
  in fact healthy starts (plausible handle `0x10052`, exactly 5 accepted
  X11 connections, no doom signature) that certification could never see,
  because the FD-48 spawn signal was never emitted on the 32-bit open
  paths. B0 is the honest shipped-state certification rate; it is not a
  clean measure of FD-02 alone.
- **No B1→F rate delta is claimed.** With the signal composed in, the
  stock Wine-10 payload also certified 3/3: at this harness and load
  profile its impatience pair did not bite in three boots. That does not
  acquit the stock module — the defects are verified present in its source
  with the same constants that measured 0/10 pre-fix on the 64-bit side
  (FD-01), and Wine 10's own null-GUID fallback (which the patch
  deliberately preserves) plausibly masks part of the latch's failure
  space at this lighter 32-bit profile: a mask, not a fix. The 10-second
  input-idle fuse and the remaining latch paths are live code in every
  shipped 32-bit copy until this payload replaces them. What this lane's
  measurement proves is that the FIXED payload starts cold, first-attempt,
  5/5 under the hardened rules; the defect's presence in the stock payload
  is proven at source level, and its 64-bit twin's bite rate is the
  campaign's measured reference.
