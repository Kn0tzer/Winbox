## Runtime settlement — read this before the deploy lane acts

The batch-17 runtime IS the fd168s4 runtime (FD-200 is script-only, FD-224
is test/tooling-only; no other runtime file changes). The fd168s4 release pin
is kept; no new 493 MB archive was cut under a batch-17 name.

Two premises in the composition brief turned out to be wrong on the facts,
and the settlement below is what was actually done instead. Both deviations
are recorded here, with the proof that the outcome is the same bytes.

**Deviation 1 — the canonical archive cannot be the gate source this time.**
The combining standard names the newest retained canonical (date-only)
archive as the gate source. The canonical archive
`backups/winbox-runtime-assets-20261107/browser-runtime-20261107.tar`
(491,182,080 B, sha256
`f54d0550bc413a34b91c1c66785a546d5122f5bdc7141ef0b374877191dab9ca`) predates
batch 11: its `wine64.zip` has 1,280 members and is missing
`usr/lib/x86_64-linux-gnu/libudev.so.1`, which batch 11 added (FD-195 — the
store's batch-11 `wine64.zip` has 1,281 members and the member is present).
Staging the canonical base could never reproduce the fd168s4 archive. The
gate therefore staged from the store's batch-11 `wine64.zip`
(`13f254e3c3a51449abfec2a3e4aba385e085f41ffee9ab53e9eb77260f2a271e`), the true
predecessor: same member set as fd168s4 (1,281), only 2 content differences
(`win32u.dll`, `win32u.so` — exactly the slice-4 changes). The prep symlink
for `web/runtime/wine64.zip` was replaced with a real copy of the batch-11
file first, so no write ever went through a preparation symlink (FD-261
hazard).

**Deviation 2 — the stage script cannot reproduce the lane's hash by itself.**
`tools/rootfs64/stage-wine8-backports.sh` writes fresh entries with
`ZipInfo` stamped "now", so a literal re-run produces a different hash every
time. Run on the composed tree it produced `1c3d4579…` (1,281 members) with
its own final verification passing (all 46 staged members hash to the repo
bytes). Content proof, read from disk: **0 content-differing members across
all 1,281** between the staged archive and the lane's `e1479bea…` archive, same
member set, same member order. The only differences were ZipInfo timestamps on
53 members (the 46 staged entries + 7 directory entries) — verified by a
structural comparison (central-directory sizes identical, zero header
mismatches ignoring time/date). The timestamps were re-stamped to the lane's
per-member values by a binary patch of the DOS time/date fields only (8 bytes
per member, local header + central entry; sizes and CRCs untouched), and the
result is **byte-identical: sha256
`e1479beaf88509cc43f093aa1630f9abe706364a8840eade1709431190e1ead5`,
195,994,432 B** — the pinned hash. Zip timestamps are build-time metadata,
not content; the re-stamp is the reproducibility mechanism, and the content
diff of 0 is the proof.

## Adjudications

### Suite re-runs: two boot timeouts — load artifact, FD-274 filed

The composition ran the `win32u-fd168-slice4` suite test twice on the composed
dist (the composition's own runtime re-proof; the product is byte-identical
to the lane-proven build, so this re-proves rather than newly proving).
Both runs failed identically at the boot wait, the fixture never reached:

- Run 1 (`test-results/merge-batch17/suite-win32u-fd168-slice4.log`):
  `FAIL win32u-fd168-slice4 (613753ms)`, `page.waitForFunction: Timeout
  600000ms exceeded` in `bootGuest` (`probe-base.mjs:162/169`). Box load
  12–16 through the run (peak 16.65).
- Run 2 (`test-results/merge-batch17/suite-win32u-fd168-slice4-run2.log`):
  `FAIL win32u-fd168-slice4 (606586ms)`, same timeout in `bootGuest`. Started
  at load 7.66, spiked to 15.16 mid-boot and 17.73 at the timeout.

Adjudication: **load artifact, not a product defect.** The composed product
is byte-identical to the build the FD-168 lane proved green twice (suite runs
2 and 3: PASS, 538,840 ms and 619,513 ms, all 21 checks ok=1, stub=0) —
wasm `bcd9d500…`, js `0312a6d4dee…`, wine64.zip `e1479bea…`, test unchanged —
so no product variable exists between the lane's green runs and these
timeouts. The lane's own negative control had the identical shape three
times (bootGuest timeouts at 600 s under load 13–19) and booted in 403 s as
load fell; the lane flagged the thin margin as a watch item. A third re-run
was not attempted: the failure shape is known, the evidence is preserved in
two runs, and the box load stayed 12–18 — a third run would most likely
time out the same way and prove nothing new.

The thin margin itself is real and now has five timeouts behind it, so it
is filed rather than left as a watch item a third time: **FD-274** (fresh
64-bit boot outruns the suite's 600 s boot wait under load; same class as
FD-264 and FD-273; fix shape is raising the wait or speeding the boot).
The gate's browser-suite re-proof of the win32u names on the composed dist
remains owed in a quiet window (or after FD-274 raises the wait); the lane's
proof on the byte-identical product stands in the meantime.

### Nothing else failed

No other non-passing item. The build, direct checks, and queue gate are all
