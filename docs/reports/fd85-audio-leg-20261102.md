# FD-85 — the common-dependencies audio stage, convicted in two layers

Lane `lane-fd85` (worktree `/home/ubuntu/wt-fd85`), based on the
`lane-fd65` tip `ed23b91c4` — FD-85 exists only on that register and
is unreachable without the FD-65 fix (the test dies at its Gecko
stage on the integration tip). Evidence: `test-results/fd85/`.
Build: clean bootstrap from the retained
`runtime-assets-20261102` archive; `bw64-build.sh` "Browser export
verified", wasm `1d46405a…` — byte-identical to the shipped build
(this lane changes no emulator code).

## The filed claim, and what measurement did to it

FD-85 as filed said: guest completes (`OPENAL: RESULT 0`), no
non-zero sample reaches the page's AudioContext capture, break
"downstream — emulator audio output/pump or the page capture path".
Both halves of that guess were wrong in an instructive way: the
capture path was indeed broken, AND the emulator's audio **input**
(not its output/pump) receives silence from the Wine leg. The filed
failure is two defects:

1. **FD-87 (found here, fixed here, closed CL-42)** — the test's
   capture watched a path guest audio no longer uses.
2. **FD-85 proper (stays open)** — Wine's audio leg delivers
   silence to the emulator for every Windows audio client tried.

## Layer 1: the capture was blind (FD-87)

`common-dependencies.test.mjs` (written 2026-10-18) counts samples
only in `ScriptProcessorNode` output buffers. On 2026-10-20 commit
`13b33d3e1` ("stream browser audio through AudioWorklet") moved the
bwPump bridge (`platform/sdl/kdspaudio.cpp`) onto an
`AudioWorkletNode` connected straight to the destination, and
updated `audio-tone.test.mjs` in the same commit to tap that node.
This test was not updated. In a session the only ScriptProcessor
output is SDL's own node, which the bwPump bypass leaves silent by
construction.

Control measurement (diag round 1, `fd85-diag.json`): a Linux ELF
(`dsptone-stereo`) writing a 440 Hz S16 sine straight to `/dev/dsp`
in the same session was heard at full scale by a worklet tap —
261,528 non-zero samples, peak 0.3662 (= 12000/32768) — and the
worklet's own `bw-audio-metrics` reported inputPeak =
outputPeak = 0.3662 with every output frame non-zero, while the
shipped capture counted **0 non-zero in 266,240 samples**.

Fix (`65cabcd67`): the capture now also taps the bridge's
AudioWorkletNode output into the same counters, using the un-wrapped
`createScriptProcessor` stored on the context — the exact pattern
`audio-tone.test.mjs` already uses. No wait or assertion changed;
the audio wait is still `__audioCapture.nonZero > 0` within 30 s.

Discrimination proof (diag round 4, `fd85-diag4.json`): a harness
installing the fixed capture **verbatim** (extracted from the
shipped test's source) counted the DSP control tone at peak
0.3662 with 143,360 non-zero samples. (The same run's OpenAL window
also showed non-zero counts at the same peak; that was the control
tone's device-drain tail — SDL holds the DSP device open until its
six seconds of queued tone drain — not OpenAL audio: the run's
console has no `S16 input first non-zero` line after the control's
device, and §Layer 2's input-side measurement is independent of the
capture. Recorded here so the figure is never quoted as an OpenAL
success.)

## Layer 2: silence at the emulator's audio input (FD-85, open)

With the capture proven able to hear, the OpenAL tone still does
not arrive — and the break is measurable **before** the page: the
standing diagnostic in `KDspAudioSdl::writeAudio` logs the first
S16 write whose peak exceeds 100 (`bwPump: S16 input first
non-zero`). Across the FD-65 lane's two fixed-build runs
(`test-results/fd65/commondep-v2/v3-console.log`) and every run on
this lane, that line fires **only** for the direct-DSP control,
never for a Wine-path device; the first converted push for the
OpenAL device is 898 frames at peak 0.0000, while the metrics
stream shows real-time byte volume (24–30 audio calls, 65–84 KB
per ~500 ms window) and the guest finishes normally.

The leg below the break is proven good in the same sessions
(direct `/dev/dsp` tone at full scale, above). The leg was then
exercised from the guest side four more ways (diag rounds 1–3,
`fd85-diag.json`, `fd85-diag2.json`, `fd85-diag3.json`):

- **OpenAL default (= wasapi):** ALSOFT log error-free; backend
  "wasapi", mix Stereo Float32 48000 Hz, buffer 480/1536;
  `RESULT 0`; silence at the input and at the worklet tap.
- **OpenAL forced `ALSOFT_DRIVERS=winmm`:** guest completes
  (`RESULT 0`), silence at the input.
- **OpenAL forced `ALSOFT_DRIVERS=dsound`:** the backend's
  playback thread logs `(EE) WaitForSingleObjectEx error: 0x102`
  (WAIT_TIMEOUT) three times and the fixture fails — the source
  never finishes. A hang face of the same leg.
- **Raw WASAPI fixture** (`tools/guest-fixtures/wasapi-tone.c`,
  committed): fills the `IAudioClient` shared buffer with the
  same sine in-process — no OpenAL, no mixer. Polling mode:
  `MIXFMT tag=65534 ch=2 rate=48000 bits=32`, `BUFFERFRAMES
  48000`; silence at the input; device consumption stalls after
  26,737 ring frames and the client hangs on full padding (it
  never printed RESULT within 90 s and held the device, which is
  why the event-driven mode run that followed is not a
  measurement). OpenAL is thereby exonerated: a textbook WASAPI
  client loses its samples in the same place.
- **Raw WinMM fixture** (`tools/guest-fixtures/winmm-tone.c`,
  committed): `NUMDEVS 1`, `PLAYSTART`, then `waveOutWrite`
  never returns within 60 s — WHDR_DONE never fires. This is the
  waveOut hang long noted in
  `web/tests/suite/unit/audio-audible-output.test.mjs`'s header,
  now reproduced on the current build as part of this leg.

Driver facts from a `WINEDEBUG=+mmdevapi` run (diag round 2):
mmdevapi's driver list is `pulse,alsa,oss,coreaudio`; winepulse
loads with priority Unavailable, winealsa Neutral and is
selected; `wineoss.drv` fails to load (126 — the staged Wine
ships no wineoss PE or unix side at all, verified against
`wine64.zip`'s member list), winecoreaudio likewise absent.

**Break point, proven:** between a Windows audio client's
successful API calls in the guest and the emulator's audio input
(`KDspAudioSdl::writeAudio`), inside Wine's mmdevapi →
winealsa → ALSA (OSS-plug) leg or its contract with the
emulator's OSS device. Not proven, and not claimed: the
sub-split between the WASAPI shared-buffer handoff, the
winealsa feeder, and the ALSA plug format/rate conversion. The
next bisection needs a probe the current fixture set lacks —
an ALSA-client program on the guest's Linux side (the dsptone
fixture bypasses ALSA entirely, which is exactly why it works)
— or a Wine-side content trace of the feeder's periods.

capture fix in (`test-results/fd85/commondep-fixed-run.log`,

capture that can hear. JS unit suite on the fixed tree:
348 passed, 0 failed (`test-results/fd85/js-unit.log`).

worker) that the FD-65 lane's two runs and this lane's
full-test run did not show (`test-results/fd85/diag5-run.log`).
