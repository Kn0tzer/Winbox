# FD-201 — 32-bit start killed by a guest memory error at the spawn transition

Lane record, 2026-11-07. Branch `lane-x86-start-fault` off integration
tip `334c70be4`. Status: **filed and analysed; reproduction and fix
pending — the lane stopped on the disk guardrail** (free space fell to
5.5G, under the ~6G stop line, while the sibling wave's build/probe
relay saturated the box). Resume steps are at the end.

**RESOLVED on the resume, later the same day — see the Resolution
addendum at the end of this record.** Cause identified and fixed
(commit `5602c1dd5`); closing terms met on the branch.

## What was filed

Register entry **FD-201** in `docs/defect-register.md` (section A,
commit `4c2093887`): a first-visit 32-bit start can be killed at the
moment a new program starts inside the session — a session worker dies
with a guest memory error and the desktop never appears. High severity.
Evidence: the batch-10 deploy record
(`docs/reports/deploy-batch10-20261107.md`) and the preserved consoles
in `wt-deploy-batch10/test-results/deploy-batch10-20261107/cert-x86/`
(boots 4 and 5 faulted; boots 1–3 and the 5-boot re-run series are
clean controls).

## What the preserved consoles establish (read directly, not from summaries)

- Both faulted boots delivered the wasm `RuntimeError: memory access
  out of bounds` at the identical console position (boot-4 line 868,
  boot-5 line 869): immediately after the wineserver's socketpair
  wiring for the session's last program start (the `cmd /c echo
  vkboot` program, emulator pid 77), where clean boots log the new
  program's `setupThreadStack32`. Identical JS glue offsets in both
  (15105 = the main thread's pthread-worker `onerror` handler in the
  shipped `boxedwine64.js`; 6378 = the worker message handler's
  rethrow after `__emscripten_thread_crashed()`), i.e. the trap fired
  inside wasm code running on one worker while it handled a message.
- The victim is the desktop program's main thread (emulator pid 73 /
  tid 74, explorer.exe): in every stall-watch dump after the fault
  (14 dumps in boot-4, 7 in boot-5) it sits at one byte-identical
  state snapshot (`args=0x7f10f5f0,0x108c6250,0x10730ff4,0x7f10faa0,
  0xc0000004,0x7f10fd48 rip=0x1042abb0 eax=0x74`) while its
  no-progress counter grows to 780 s. Its worker never runs again;
  every other thread in those dumps is alive (blocked on ordinary
  waits, snapshots changing between dumps). Explorer never creates
  its post-start threads (tid 80/81 in clean boots), the desktop
  never reports ready, and both boots exhaust the 900 s budget with
  0 restarts. Other processes keep working for a while after the
  fault (the new program starts, echoes, exits) — exactly one worker
  died.
- At the fault moment the desktop program was in early
  initialization: it had created its first two server socketpairs
  and its manifest (actctx) parsing messages appear in the console
  immediately before the fault.
- Incidence is bursty, not load-explained: boots 4 and 5 faulted
  back-to-back (boot 5 at near-zero load) after three clean boots,
  and the re-run series ~80 min later went 5/5 at higher load. The
  shipped program code did not change in batch 10 (wasm
  byte-identical to batch 9), and one earlier instance of the same
  failure shape is on record against the batch-4 shipped build.

## Ruled out during analysis

- The one identity-cast bulk copy in the kernel
  (`KMemory::ensureContinuousNative_unsafe`, kmemory.cpp:1448, which
  memcpys from a guest page number cast directly to a host pointer)
  is reachable only from the legacy 32-bit GL vertex marshaller
  (`glMarshalVertex.cpp`), and that file is compiled out of the
  browser build: the `wasm64-mt` target defines
  `BOXEDWINE_GUEST_X64=1` and the marshaller is gated on
  `!defined(BOXEDWINE_GUEST_X64)`. Not the shipped fault. (The
  function remains a latent trap for any future caller in a build
  where it is reachable; noted here, not filed separately.)
- The RAM page allocator (`soft_ram.cpp`) never unmaps: released
  pages recycle through a free list inside permanent chunks, so a
  stale page pointer reads recycled content but cannot leave the
  wasm memory. `KMemory::getRamPtr` already refuses cross-page
  spans with a counted BW64-FAIL and nullptr.
- The interpreter's per-access softmmu path translates every access
  through the page objects; it holds no long-lived raw pointers.

## Why the lane stopped

Free disk fell 12G → 8.4G → 5.5G over the lane's first hours as the
sibling wave's from-scratch builds consumed it, crossing the ~6G
stop line in the lane's guardrails; concurrently the shared build
lock and the heavy probe slots were held in a continuous relay by
sibling lanes (the known build-pending/probe-starvation shape), so
the reproduction could not start (the diagnostic build completed in
a gap — see above). The lane's generated build state was stripped
before reporting, returning the tree to 424M; the reproduction
process was stopped while it waited for a probe slot (zero boots
run).

### Identification (on the shipped wasm itself)

The shipped wasm has no name section, and the lane's surviving
`BW64_PROFILE=1` build (`f5ff0b8c…`) cannot supply one: it has
the same defined-function count (10,635) but different function
bodies at all six stack indices, and the names at those indices
are unrelated functions. (This is the measurement behind the
corrections in "Prepared for the resume" above: profile-build
indices do not transfer to the shipped build.)

Disassembling the shipped wasm directly:

- `func[7915]` writes a guest struct field-for-field identical
  to the 32-bit `struct sysinfo`: uptime (a no-arg time call,
  adjusted, /1000) at +0, three zero loads at +4/+8/+12,
  two i64 results — each shifted right 12 — at +16/+20, zeros
  at +24..+36, a 16-bit value read from a global at +40, a
  16-bit zero at +42, zeros at +44/+48, and the constant 4096
  at +52. That is `KSystem::sysinfo` (ksystem.cpp): writed =
  its field writes, the +40 value is the process count,
  4096 is `mem_unit = K_PAGE_SIZE`.
- `func[1971]`, called by it with two i64 out-pointers, writes
  the sentinel 0x100000000 (2^32) to the first out-pointer,
  then scans a global table of 16-byte slots (begin/end in
  adjacent globals), skipping slots whose byte at +12 is
  clear; for each occupied slot it takes the pointer at +4
  and — after a null check — loads the field at +248. **That
  load, at wasm offset 0xbe6c3, is the trap.** It then walks
  a list at +16 of the pointed-to object under a lock at +40,
  counting flagged nodes scaled by <<12, and adds a called
  function's result at the entry's +112 field, also <<12.
  That is `KSystem::guestRamInfo`: total = 4 GiB, committed
  summed over the process table; +248 is
  `KProcess::memory64` (the walk is
  `KMemory64::mappedCommittedPageCount`, inlined: pagesMutex
  at +40, the pages container at +16), +112 is
  `KProcess::memory` (the call is
  `KMemory::allocatedPageCount`).

### The cause

`KSystem::processes` is a `BHashTable<U32, KProcessPtr>`:
slots of 16 bytes — key at +0, the shared_ptr (pointer at +4,
control block at +8), `used` bool at +12 — exactly the layout
the compiled scan reads. `guestRamInfo` iterated it with **no
lock**. Every other access in the class holds
`processesCond`: `addProcess` (set) and `eraseProcess`
(remove) mutate under it, as do `getProcess`, `kill`,
`reapChild`, and `getRunningProcessCount`'s identical
iteration.

BHashTable grows by wholesale replacement: when an insert
crosses the load-factor limit (count ≥ 3/4 of slots — at 6,
12, 24, … processes), `rehash()` moves the slot array out,
installs a new one at double size, re-inserts every entry,
and frees the old array on return. An unlocked scan in flight
across that moment keeps reading the freed array (the compiled
iterator re-reads the vector's begin/end as it advances);
freed heap is promptly reused by the process-start work going
on around it, so the scan reads garbage slots — an occupied
byte set and a wild pointer at +4. The null check passes
(the pointer is non-null garbage) and the first field load,
`process->memory64`, lands outside the wasm memory and
traps. The worker dies; the guest thread it was running
freezes mid-start (the deploy boots' frozen explorer main
thread is its last guest state); the desktop never reports
ready.

Why it strikes exactly at program starts, in bursts, at any
load: the caller is a starting process's own `sysinfo` —
every Wine process issues it during start-up — while sibling
starts are inserting processes into the same table. A rehash
happens only when an insert crosses a power-of-two count, so
most start bursts never open the window; when one does, any
concurrent sysinfo scan can fall through it. This also
retires the question the original analysis left open: the
victim is whichever thread calls sysinfo inside the window,
not a fixed thread, and no guest-side pointer path is
involved (the earlier ruled-out items stand).

### The fix (commit `5602c1dd5`)

- `KSystem::guestRamInfo`: the scan now runs under
  `BOXEDWINE_CRITICAL_SECTION_WITH_CONDITION(processesCond)`.
- `KSystem::processCount`: the size read now takes the same
  lock (it could observe the table mid-rehash).
- `KSystem::sysinfo` (32-bit): the procs field now goes
  through `processCount()` instead of reading the table size
  directly. The 64-bit sysinfo already used `processCount()`.
- Regression guard: the guest CPU topology test
  (`testGuestCpuTopology`, which already exercises
  `guestRamInfo`) now also fails unless both functions carry
  the lock, so the lock cannot be removed as an optimization.

Deadlock review: no caller of `guestRamInfo`/`processCount`
holds any lock (the 32-bit and 64-bit sysinfo handlers, the
/proc/meminfo open, one unit test — verified by grep over the
tree). Inside the lock the fix calls only the per-memory
counters: `mappedCommittedPageCount` takes that memory's own
pagesMutex, `allocatedPageCount` takes none; no path takes a
memory lock and then `processesCond`. The hold is a bounded
table scan, the same shape `getRunningProcessCount` already
performs under this lock.
