# FD-201 — 32-bit start killed by a guest memory error at the spawn transition

Lane record, 2026-11-07. Branch `lane-x86-start-fault` off integration
tip `334c70be4`. Status: **filed and analysed; reproduction and fix
pending — the lane stopped on the disk guardrail** (free space fell to
5.5G, under the ~6G stop line, while the sibling wave's build/probe
relay saturated the box). Resume steps are at the end.

## What was filed

Register entry **FD-201** in `docs/defect-register.md` (section A,
commit `4c2093887`): a first-visit 32-bit start can be killed at the
moment a new program starts inside the session — a session worker dies
with a guest memory error and the desktop never appears. High severity.
Evidence: the batch-10 deploy record
(`docs/reports/deploy-batch10-20261107.md`) and the preserved consoles
in `wt-deploy-batch10/test-results/deploy-batch10-20261107/cert-x86/`
(boots 4 and 5 faulted; boots 1–3 and the 5-boot re-run series are
clean controls).

## What the preserved consoles establish (read directly, not from summaries)

- Both faulted boots delivered the wasm `RuntimeError: memory access
  out of bounds` at the identical console position (boot-4 line 868,
  boot-5 line 869): immediately after the wineserver's socketpair
  wiring for the session's last program start (the `cmd /c echo
  vkboot` program, emulator pid 77), where clean boots log the new
  program's `setupThreadStack32`. Identical JS glue offsets in both
  (15105 = the main thread's pthread-worker `onerror` handler in the
  shipped `boxedwine64.js`; 6378 = the worker message handler's
  rethrow after `__emscripten_thread_crashed()`), i.e. the trap fired
  inside wasm code running on one worker while it handled a message.
- The victim is the desktop program's main thread (emulator pid 73 /
  tid 74, explorer.exe): in every stall-watch dump after the fault
  (14 dumps in boot-4, 7 in boot-5) it sits at one byte-identical
  state snapshot (`args=0x7f10f5f0,0x108c6250,0x10730ff4,0x7f10faa0,
  0xc0000004,0x7f10fd48 rip=0x1042abb0 eax=0x74`) while its
  no-progress counter grows to 780 s. Its worker never runs again;
  every other thread in those dumps is alive (blocked on ordinary
  waits, snapshots changing between dumps). Explorer never creates
  its post-start threads (tid 80/81 in clean boots), the desktop
  never reports ready, and both boots exhaust the 900 s budget with
  0 restarts. Other processes keep working for a while after the
  fault (the new program starts, echoes, exits) — exactly one worker
  died.
- At the fault moment the desktop program was in early
  initialization: it had created its first two server socketpairs
  and its manifest (actctx) parsing messages appear in the console
  immediately before the fault.
- Incidence is bursty, not load-explained: boots 4 and 5 faulted
  back-to-back (boot 5 at near-zero load) after three clean boots,
  and the re-run series ~80 min later went 5/5 at higher load. The
  shipped program code did not change in batch 10 (wasm
  byte-identical to batch 9), and one earlier instance of the same
  failure shape is on record against the batch-4 shipped build.

## Ruled out during analysis

- The one identity-cast bulk copy in the kernel
  (`KMemory::ensureContinuousNative_unsafe`, kmemory.cpp:1448, which
  memcpys from a guest page number cast directly to a host pointer)
  is reachable only from the legacy 32-bit GL vertex marshaller
  (`glMarshalVertex.cpp`), and that file is compiled out of the
  browser build: the `wasm64-mt` target defines
  `BOXEDWINE_GUEST_X64=1` and the marshaller is gated on
  `!defined(BOXEDWINE_GUEST_X64)`. Not the shipped fault. (The
  function remains a latent trap for any future caller in a build
  where it is reachable; noted here, not filed separately.)
- The RAM page allocator (`soft_ram.cpp`) never unmaps: released
  pages recycle through a free list inside permanent chunks, so a
  stale page pointer reads recycled content but cannot leave the
  wasm memory. `KMemory::getRamPtr` already refuses cross-page
  spans with a counted BW64-FAIL and nullptr.
- The interpreter's per-access softmmu path translates every access
  through the page objects; it holds no long-lived raw pointers.

## Why the lane stopped

Free disk fell 12G → 8.4G → 5.5G over the lane's first hours as the
sibling wave's from-scratch builds consumed it, crossing the ~6G
stop line in the lane's guardrails; concurrently the shared build
lock and the heavy probe slots were held in a continuous relay by
sibling lanes (the known build-pending/probe-starvation shape), so
the reproduction could not start (the diagnostic build completed in
a gap — see above). The lane's generated build state was stripped
before reporting, returning the tree to 424M; the reproduction
process was stopped while it waited for a probe slot (zero boots
run).

## Resume steps

   relay.
2. Run the reproduction against the live dist:
   `DIST=/home/ubuntu/kn0tzer/winbox N=12 TAG=repro-live-2 node web/tests/x86-fault-repro.mjs`
   (repeat series until at least one fault is captured; incidence
   was 2/10 in the deploy window and 0/5 in the re-run window).
3. From the captured stack, identify the trapping function (index →
   name via a `BW64_PROFILE=1` build of this branch when the build
   lock is obtainable).
4. Fix the cause on this branch, then prove: repeated 32-bit starts
   against a build of the fixed branch (the reproduction driver,
   `DIST=dist`) pass with zero occurrences of the failure — a series
   at least as large as the faulting window (≥10 boots) — plus the
   standard light checks through the checking queue.
5. Move FD-201 to section B of the register with the fixing commit
   and this proof; the closure number settles when batches combine.
