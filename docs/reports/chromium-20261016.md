# Chromium 109 startup: 2026-10-16

Chromium 109.0.5414.120 (x86) now displays an offline page and runs its
JavaScript with software-only launch settings. Rendering, mouse clicks, and
typing into an initially empty field are verified. The HADDPD crash,
font-initialization stack overflow, stale X11 focus, and missing Arial font
metrics are fixed. Performance tuning and Portal work remain. Internet
browsing has not been verified.

## First crash and repair

The earlier Unix exit logs reported zero because Wine's threads exited after
the Windows process was killed. The Wine server trace establishes that
Crashpad requested `terminate_process(handle=007c, exit_code=-36862)`.
Crashpad defines `0xffff7002` as a failed initial process snapshot:
[termination_codes.h](https://github.com/chromium/crashpad/blob/main/util/win/termination_codes.h).
The trace also records the failed cross-process memory read.

The preceding exception was on a Chromium worker, at chrome.dll RVA
`0xcebc25`: `66 0f 7c ff` (`HADDPD xmm7,xmm7`). CPU32's decoder entry
for this instruction was missing. The register-only instruction consequently
raised an access violation at address `0xffffffff`.

CPU32 now decodes register and memory HADDPD and sums each operand's two
double lanes. Both operands are copied before writing the destination, so
`HADDPD xmm7,xmm7` produces the same sum in both lanes.

  `MOVDDUP MOVSLDUP MOVSHDUP HADDPD PAGE_GUARD RESULT 0`.
- `pnpm test`: legacy checks and all 121 suite groups pass after removal of
  the previous thread's temporary exit diagnostics. The diagnostic patch is

- `pnpm typecheck` passes.

## Font-initialization stack overflow

The first Chromium run after the repair passes the old worker crash point,
but overflows the main thread's stack at about 44.5 seconds. Wine reports
`EXCEPTION_STACK_OVERFLOW`, EIP `7bd24267`, in `RtlWakeAddressAll`.
The failure also occurs in normal multi-process mode. A stack dump reveals
the same six Chromium font-initialization frames repeating. The reduced
GDI/DirectWrite probe reports one font family (DejaVu Sans), no Tahoma, and
`DWRITE_E_NOFONT` (`88985002`) for `CreateFontFromLOGFONT(Tahoma)`.
Chromium's default-font fallback reenters initialization when that family
cannot be created.

Wine32's package omitted the architecture-independent Wine fonts that are
already present in the pinned Wine64 package. Adding those files to Wine32's
`/opt/wine-stable/share/wine/fonts/` changes the probe to six families, Tahoma
present, and successful DirectWrite font creation. The new `win32-fonts`
browser regression verifies GDI metrics and the DirectWrite family/mapping.

The export now stages those fonts in `glibc-rootfs32.zip`, leaving all pinned
source archives unchanged. Font hashes and the derived archive hash are
recorded in `wine32-font-provenance.json` and included in the runtime evidence
fingerprint. Unit checks preserve original archive members and verify
idempotency and failure before mutation if required fonts are missing.

## Software rendering

With the fonts restored, normal multi-process Chromium maps a window after
about 29.7 seconds and remains alive for the 150-second observation. Its
window is mostly black with a small colored line, so this does not establish
readable rendering or interaction. The earlier minimal Win32 window renders
white pixels and readable text. Software-only compositor/occlusion settings
produced readable Chromium UI and the offline smoke page in
`test-results/chromium-software-smoke/`. The page set its title to
`BW_RENDER_OK` and displayed a completed one-million-iteration JavaScript loop
(`2468 ms` in that run). This configuration adds `--single-process`,
`--in-process-gpu`, `--disable-software-rasterizer`, `--use-gl=disabled`,
`--disable-features=CalculateNativeWinOcclusion,DirectComposition`, and
`--disable-backgrounding-occluded-windows` to the earlier GPU-disabled flags.
The individual required switches have not yet been isolated.

The permanent font export passes its Wine32 browser regression, all 122 fast
suite groups plus legacy tests, and the archive/fingerprint provenance tests.

Raw evidence remains in `test-results/chromium-resume-server/`,
`test-results/chromium-resume-seh/`, `test-results/suite-cpu32-sse3/`, and
`test-results/chromium-haddpd-first/`. A passing instruction fixture does
not establish successful Chromium rendering or browsing.

## X11 input focus

The first rendered-page click test left host events queued indefinitely. The
input snapshot reported a nonzero focus XID with no registered window or
owner; Chromium had destroyed a temporary focused window. X11 now clears
focus when a window is unmapped or destroyed, and when its app is removed.
When routing falls back to the presented window, it emits FocusIn and the
advertised WM_TAKE_FOCUS notification so Wine can activate its native target.

The focused-window destruction/unmap regression fails before the cleanup
and passes after it. All 122 fast suite groups and legacy tests pass. The
real Wine32 input witness also passes mouse, key-down/up, and newly added
WM_CHAR checks for letters and space.

Chromium's page now observes a real mouse click and increments its counter.
The text-insertion check remains open: X11 delivers all keyboard events and
the page observes correct keydown names targeted at the input, but its value
does not change. The independent Win32 witness establishes character
translation for ordinary Wine32 windows; it does not establish Chromium's
Windows text-service behavior. Normal multi-process mode and Chromium 109's
TSFImeSupport feature are being compared next.


## Empty fields and DirectWrite fallback: 2026-10-17

Native Chromium address-bar typing worked, and the page received correct
keydown and keypress events, but empty HTML fields had no caret. Disabling
TSF, replaying native activation, and holding keys longer did not fix it.
The Unicode Win32 character witness passed, including immediate PeekMessage
of WM_CHAR inside WM_KEYDOWN. A seeded HTML field accepted typing; an empty
one rejected even document.execCommand('insertText').

A canvas/font comparison isolated the cause. Arial had zero width, ascent,
and descent; installed Tahoma and DejaVu Sans had valid metrics and created
a caret. Blink's Windows last-resort font list includes Arial and several
Windows families absent from this small Wine image, but not DejaVu Sans.
Wine's HKCU Software\Wine\Fonts\Replacements mechanism exposes family
aliases to both GDI and DirectWrite. An Arial-to-DejaVu Sans alias alone
restored empty-field typing without changing the page's selection or input
handlers.

The browser export now adds that alias only to its derived Wine32 user
registry. Pinned source archives and unrelated registry entries remain
unchanged. The font provenance records the registry hash, and desktop-helper
provenance records prefix hashes after both export steps.

The reduced DirectWrite regression failed before the change with
`ARIAL=0 METRICS=0 RESULT 4`, then passed with `ARIAL=1 METRICS=1 RESULT 0`.
Registry tests cover idempotency, existing aliases, CRLF, unrelated sections,
and archive preservation. All 122 fast suite groups plus legacy checks and
type checking pass.

The cleaned acceptance probe `web/tests/chromium-probe.mjs` serves the real
Chromium archive, verifies readable pixels by OCR, clicks the page, types
`boxedwine works` into its initially empty field, and checks a JavaScript
checksum. It contains no selection, text-insertion, or font-style workaround.
`test-results/suite-chromium-Arial-acceptance/` passes against the permanent
export: page ready 28.858 s, input verified at 38.151 s, loop samples
698 / 655 / 142 / 135 ms. These are initial observations, not an optimization
claim; later comparisons must use identical fixtures and idle conditions.

The downloaded Chromium archive already uses ZIP_STORED, so converting that
archive to stored entries offers no decompression improvement.


## Initial performance experiments and measurement protocol

The original automatic benchmark overlapped screenshot/OCR work and initial
painting, so its loop times are unsuitable for compiler comparisons. Workload
`integer-sum-v2` runs eight trials only after rendering, click, and empty-field
typing acceptance, triggered by a separate visible button. OCR finishes before
the workload starts. Samples five through eight describe the warmed loop;
startup readiness and input delivery are separate observations. The probe
records actual event arrival for click latency, OCR locations for each control,
a fresh input-focus event, and guest mouse targets in its evidence.

The first quiet run (`suite-chromium-bench-v2-base-2`) passes and records
427 / 423 / 103 / 104 / 104 / 106 / 104 / 103 ms, checksum 1783293664.
These new loop samples must not be compared as an optimization against the
old overlapping-OCR workload.

A private all-stored Wine32 archive preserved every file and permission but
expanded from 236,709,881 to 768,819,686 bytes. It eliminated backward stream
reopens. Under the original fixture its first two ready times were 30.595 /
31.352 s, against 28.704 / 30.449 s for interleaved baseline runs. A diagnostic
repeat took 32.113 s. There is no measured startup gain, so the variant is
rejected. Its SHA256 is
`c44a8a732e56eeb190bd4149f426926bab7946f951f145bbc9189cc39322ba47`.

The second stored-Wine run also failed to focus the input after clicking the
button; its screenshot and event snapshot are retained in
`suite-chromium-perf-stored-wine-2`. An instrumented repeat showed correct
mouse targets/focus and passed. The cause of that failed click is unresolved;
a successful repeat does not close it. The production archive remains
unchanged, and later comparisons require observed field focus before typing.
