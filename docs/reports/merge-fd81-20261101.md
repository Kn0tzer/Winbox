## Notes

- What the batch carries, in the lane record's terms
  (`docs/reports/fd81-temp-link-pattern-20261101.md`):
  in the browser build the Emscripten backings
  (MEMFS/IDBFS) define no hard-link operation, so
  FD-60's host `::link()` path could never succeed
  there — every regular-file link was refused with
  EMLINK (errno 34, the value on all 285 deploy
  lines), although the sources are ordinary files
  and the pattern succeeds on the host. The fix
  serves the pattern at the emulator layer with true
  shared content (a second node, same id, same link
  group, same backing path — not a copy), with the
  group's sharedBackingPath flag supplying the link
  counts, detach-only unlink and guest-tree-only
  rename the host filesystem used to answer for
  free. Native builds keep every refusal; symlink
  and non-file sources keep FD-60's behaviour. Its
  stated residuals stand in FD-81/CL-33 (group-
  liveness lag, cold-rescan separation, guest-tree-
  only existence).
- The branch carried the browser build in its own
  evidence (the FD-58..60 lesson applied), and the
  gate confirms the value of that: the composed dist
  reproduced the branch's wasm byte for byte, so no
  composition-time repair of any kind was needed —
  the only settlement is the numbering/closure one.
- The gate ran under shared-box load (the FD-77
  follow-up lane active in its own tree throughout);
  all probes ran through the slot system, no sibling
  process, build or tree was touched, and no test
  runner was stopped by pattern. Disk 18G free at
