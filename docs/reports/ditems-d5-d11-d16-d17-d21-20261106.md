## D16 = FD-11 — `BString::split("")` infinite loop

`BString::split(const char*)` matched the empty delimiter
at the cursor forever and never advanced. The guard now
lives inside `split` itself: an empty (or null) delimiter
returns the whole string as the single result, covering
every caller rather than only the filesystem layer's
guarded entry point (`source/util/bstring.cpp`).

Proof — native test `testBStringSplit`: on the unpatched
code the test does not fail, it hangs; the RED log
(`red-main-testBStringSplit.log`) is a timeout kill after
the banner. On the fixed code it passes, with `split('/')`
and `split("::")` controls unchanged
(`green-main-testBStringSplit.log`,
`green2-main-testBStringSplit.log` after the restore
rebuild).

## D11 = FD-14 — fault reporting's two blind spots

(a) `CPU64::raiseSyncFault` logged nothing itself, so the
direct kernel-side caller (rt_sigreturn's bad-frame path)
delivered faults in silence. It now logs at the delivery
point, just before returning success: a rate-limited
`BW64-FAIL sync-fault64 pid=.. tid=.. sig=.. trap=..
addr=.. err=.. si_code=.. delivered=1 count=..` line
(first 64 deliveries, then every 1024th — the flood
discipline of the interpreter funnel). Refused deliveries
log nothing. The funnel lines in `cpu64.cpp` are
unchanged: they record fault occurrence; the new line
records delivery, which is the point FD-14 named.

Proof — native x64 test
`testRaiseSyncFaultDeliveryLogged64`: RED on the
unpatched code ("raiseSyncFault delivery produced no
delivery-point log line",
`red-x64-testRaiseSyncFaultDeliveryLogged64.log`);
GREEN after, with the actual emitted line in the log
(`green-x64-testRaiseSyncFaultDeliveryLogged64.log`):
`BW64-FAIL sync-fault64 pid=-1 tid=-1 sig=11 trap=14
addr=0xdead0000 err=5 si_code=2 delivered=1 count=1`
(pid/tid -1 in the thread-less fixture, by design). The
test loops fresh-fixture deliveries because the
production counter is process-wide and rate-limited;
the loop is the deterministic shape. It uses a test-only
log-capture hook in `source/util/log.cpp` /
`include/log.h` (`bw64TestLogClear` /
`bw64TestLogContains`, compiled only under `__TEST`,
hooking the single `internal_log` funnel).

(b) The 32-bit core's two gate sites were confirmed in
their own context — already correct, no code change:
`normal_invalid` and `normal_ud2` in
`source/emulation/cpu/normal/normal_other.h` recover-gate
exactly as the 64-bit mirrors do (skip logged once per
RIP via `bw64RecoverClaimRip`, bounded per RIP; the
fall-through delivers through
`KThread::signalIllegalInstruction`, which logs via
`bw64LogGuestFault32`). The gate semantics match the
standing rule: the switch gates only the logged skip
departure, never the delivery.

## D17 = FD-196 (new) — `translateOpenError` collapsed errnos

`KProcess::translateOpenError()` mapped only
EACCES/EEXIST/ENOENT/EISDIR and turned every other host
open failure into -EINVAL. The filesystem layer already
preserves the host errno exactly (`FsFileNode::open`
saves it, logs non-ENOENT/ENOTDIR failures, restores it
before returning nullptr), so the map now covers 25
errnos; `K_EMLINK` (31) and `K_EOVERFLOW` (75) were added
to `include/kerror.h`. The -EINVAL default stands only
for node types that return nullptr with no host errno
(virtual / dynamic-link / memory nodes) — for those it
is the honest answer. Sole call site:
`KProcess::openFileDescriptor`.

Proof — native test `testTranslateOpenError`, a 28-row
table (4 pre-existing mappings as controls, 21 widened
errnos, 3 default rows): RED on the unpatched code
(`red-main-testTranslateOpenError.log`), GREEN after
(`green-main-testTranslateOpenError.log`).

## D5 = FD-195 (new) — seg_mapper/seg_access caller audit

Both functions with `throwException=false` promise a
delivered fault instead of a throw; with no guest handler
they log, kill the process, and throw unconditionally
(already on record as FD-36(d)). The audit read every
call site:

- The four explicit-false sites are sound:
  `CPU::startException` (re-fetches the op at the handler
  address after delivery), `CPU::runNextSingleOp`
  (re-fetch plus a loud panic if there is still no op),
  `NormalCPU::run` (same shape, panics with pid/tid/
  address), and the multi-threaded platform's containment
  site (catches, retires the thread cleanly — the FD-41
  shape).
- The default-true callers are sound because both
  functions throw on every path that does not return
  from the on-demand mapping: the softmmu read/write and
  code pages, and `KMemory::preflightWrite`.
- One real defect: the invalid page's six accessors
  called `seg_mapper` and returned. When the on-demand
  mapping succeeded (the 32-bit Wine syscall-frame
  window), reads returned a fabricated 0 and writes were
  silently dropped. All six now re-dispatch through the
  page's current type after `seg_mapper` returns — the
  shape `CodePage` already used — and a write that still
  cannot land logs `BW64-FAIL invalid-page-write ...
  outcome=dropped` instead of vanishing. Audit
  observation, no filing: the soft read/write page
  accessors would dereference a null page pointer if
  `seg_access` ever gained a return path; today it
  cannot return to them.

Proof — native test `testFaultDelivery32` additions:
write/read-back of byte, word, and dword through the
on-demand-mapped window (0x76F040..) on a fresh fixture.
RED on the unpatched code (the dropped write fails the
readback; `red-main-testFaultDelivery32.log`), GREEN
after (`green-main-testFaultDelivery32.log`), and the
pre-existing fault-delivery cases in the same test pass
unchanged. The fresh-fixture read control returns 0,
pinning that the fabricated-0 behaviour is preserved
exactly where it was correct (a fresh anonymous page is
zero-filled — now served by the re-dispatched real
page).
