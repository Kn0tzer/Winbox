## The futex flaw: real, live at the integration tip, now fixed

The 32-bit futex implementation was missing the protections the
64-bit implementation received earlier:

1. FUTEX_WAKE skipped any registered waiter whose `waiting` flag
   was not yet set — a wake arriving in the window between a
   waiter claiming its slot and parking in it was lost.
2. A FUTEX_WAKE that arrived before its waiter registered was
   dropped entirely. For stateless waits — Wine's
   alert-by-thread-id futex, whose word is 0 on both sides, so the
   waiter's word recheck can never fire — that is unrecoverable:
   the waiter parks forever at ~0 host CPU.

Proof on the unfixed code (integration tip), native test,
`test-results/fd12/native-test-RED-unfixed.log`:

- scenario 1 (deterministic): a WAIT issued after its WAKE was
  lost returned -ETIMEDOUT after the full 400 ms;
- scenario 3 (race): 1 of 120 wake-before-park rounds lost the
  wake.

Proof on the fixed code: the same test passes 6/6 runs
(`native-test-GREEN-fixed.log`); the full native suite is
664/664 (663 baseline + the new test,
`native-full-fixed.log`) and the x64 suite 63/63
(`native-x64-fixed.log`); the JS unit suite against the fixed
dist build is 346/0 (`js-unit-fixed.log`). The dist build of
the fix is git_sha `e8644f814`, wasm `f31851fd...`
(`BUILD_INFO-fixed.json`).

## The park in vivo: characterized, not convicted

The consumer-path failure (Chromium demo, 32-bit guest) was
reproduced repeatedly on 2026-11-01, including twice on the
fixed build. Its signature is exact and identical in every
instance, including the deployment capture that opened this
lane (integration tree, `test-results/deploy-fd53-fd55pipe-
20261101/chromium-consumer/` attempt 1):

- the session boots completely (desktop process, display
  connections, guest Chromium started and fetching);
- the guest log's last fetch milestone is `fszipurl: ...
  MB fetched lazily so far` (192 MB in most captures,
  112 MB in one); in the captures with fine-grained console
  timing the console's last line is a persist sync at
  76-78 s in;
- then total silence: the window never maps, no error is
  logged anywhere, no BW64-FAIL fires. In a clean run the very
  next guest lines after the same 192 MB mark are the first
  window mapping. The stall therefore sits inside guest
  Chromium's startup thread rendezvous, after its binaries
  load and before its first window.

Incidence on 2026-11-01 (Chromium demo, this harness; "armed"
means the thread-dump instrumentation configuration):

| build | configuration | mapped | parked |
|---|---|---|---|
| live `103032872` (unfixed) | armed, dump vacuous (see below) | 3 | 2 |
| fixed `e8644f814` | uninstrumented | 0 | 2 |

## The dump gap (found and fixed in this lane)

`bw64_dump_guest_threads()` enumerated tids up to a bound that
was only ever raised inside the 64-bit syscall dispatcher, so
during a 32-bit session every dump reported `maxTid=0`,
`dumped=0` — a successful-looking empty dump while dozens of
guest threads were running. Two of this lane's baseline
reproductions carried 20 such vacuous dumps each. The dump's
own 32-bit reporting branch existed and was never reached.
`80062923f` factors the tid note into a shared helper called
from both dispatchers; dumps in a 32-bit Chromium session now
enumerate the real threads (maxTid=191 observed, with state,
syscall, args and wait-condition name per thread — e.g. the
healthy steady state: most threads blocked reading the
wineserver socket, a handful in futex waits, one waiter per
address). This is the instrument a follow-up capture needs:
the first parked run under the armed configuration will show
exactly which threads wait on what.

## The parked-state capture (hunt-4) and the freeze mechanism

One armed run (consumer-hunt-4) did park, and its working
thread dumps are the conviction artifact
(`test-results/fd12/consumer-hunt-4/`). Findings:

- The session was healthy until ~64 s (192 MB fetched), GL
  contexts were being created at 63-68 s, the last guest line
  is a persist sync at 78.4 s; after that, only thread dumps.
- Every dump from ~336 s to ~426 s is BYTE-IDENTICAL per
  thread: 69 threads, none progressing at all over 90+
  seconds. Sixteen threads sit in futex waits (fourteen of
  them Wine per-thread alert words in one process, one waiter
  each — the normal idle pattern, only more of them), 42 in
  wineserver-socket reads, one in a timed poll — and TEN
  threads of the main guest process show as "running" with
  frozen registers at guest DLL addresses. A healthy session
  at the same phase has zero such threads: every thread is on
  a named condition.
- The fetch layer never spoke again: no stall-watchdog line,
  no retry, no failure in any parked run's console, although
  the fetch code's own documented worst case (60 s stall
  window, 3 retries, 240 s waiter deadline) should have
  produced a loud failure within ~3-4 minutes. The freeze
  lasted 347+ seconds. The blocking fetch therefore never
  entered its retry loop: the guest thread was stuck before
  or inside the proxied fetch call whose main-thread service
  never came.
- Why one stuck fetch freezes EVERYTHING is proven in code:
  `FilePage::onDemmand` (source/emulation/softmmu/
  soft_file_map.cpp) performed the backing-file read —
  for a lazily fetched archive, a blocking network fetch
  proxied to the browser main thread — while holding the
  per-process memory mutex. Every other thread of the
  process that faults on an unresident page (or otherwise
  needs that mutex) piles onto it invisibly: no waiting
  condition, no log, no timeout. Their dump lines are the
  ten "running" threads frozen at their faulting
  instructions.

The fix (commit `6ddd9cdd9`) applies the fetch layer's own
discipline one layer up: the backing read in
`FilePage::onDemmand` no longer happens under the memory
mutex. The page is resolved under the lock; the read happens
unlocked; on re-entry the page state is re-validated —
a concurrent installer wins and the duplicate copy is
discarded, and the system-cache fast path still completes
entirely under the lock. A fetch that stalls now strands
only its own thread (and the fetch layer's existing
deadlines then fail it loudly); it cannot freeze the
process. What still needs its own follow-up (FD-75): why
the proxied fetch's main-thread service sometimes never
arrives at all — the capture narrows it to that service
path but cannot separate its sub-mechanisms from outside.

## Verification of the fault-path fix (`6ddd9cdd9`)

- Full native suite 664/664 — "0 tests FAILED in 262s" —
  and x64 suite 63/63, both run serially (the suite's
  canonical form), including the FD-12 futex test and the
  mmap/file tests. Logs: `test-results/fd12/
  native-full-fix2.log`, `native-x64-fix2.log`. (An
  earlier 4-worker invocation of the main suite wedged
  partway and was stopped by exact pid; the canonical
  invocation is serial and the serial run is the
  evidence.)
- JS unit suite 346 passed / 0 failed against the
  fault-path-fixed dist (`js-unit-fix2.log`); the dist
  build completed with its export verification.
- Consumer runs, uninstrumented, dist of `6ddd9cdd9`
  (dirs `consumer-verify-1..4`): verify-1 mapped 46.6 s,
  verify-3 mapped 39.0 s, verify-4 mapped 35.2 s;
  verify-2 did not map within the 600 s cap and its
  guest log carries the identical silent signature —
  last fetch milestone 192 MB, last console line the
  persist sync at 76.2 s, no fetch failure lines, no
  BW64-FAIL.

Two further armed runs on the same build
(`consumer-posthunt-1..2`) both mapped (39.0 s and
33.4 s, 8 frames each), for a fixed-build total of
5 mapped / 1 parked in 6 runs; no parked armed capture
exists on the fixed build yet, so the constellation
comparison is still outstanding.

Read honestly: the fault-path fix is associated with a
real improvement (1 of 4 mapped without it, 3 of 4
with it, same configuration) and its mechanism is
code-proven, but one identical silent park survived
it, so the freeze is not solely the amplifier:
something still occasionally stalls the session at the
same life point (~76 s, after the fetch milestones
complete) without tripping any of the fetch layer's
loud-failure paths. FD-75 stays open on that residue.
The capture instrument that can see it (the FD-74 dump
fix) is in place: the next parked capture on a
fault-path-fixed build will show whether the frozen
constellation changed (a single stranded fetcher — the
fetch service itself) or persisted (a blocker this
lane did not find).
