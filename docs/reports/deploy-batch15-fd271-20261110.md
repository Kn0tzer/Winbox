## Adjudication — consumer driver tab crashes (b1, b6, b8)

- b1, b6, b8 each exited 1 with the probe driver's error
  `page.evaluate: Target crashed` / `page.screenshot: Target
  crashed` — the test browser's tab (the renderer hosting the
  emulator page) died during metrics sampling (b1 after a full 437 s
  run, b6/b8 ~3 min in). The guest consoles carry ZERO fault lines
  of any kind (b1: 0 memfault, 0 `0xfffffd08`, 0 first-op; b6: same;
  b8: the crash came before the console file was written, 16 metrics
  lines show the guest alive until the crash). No guest verdict is
  recorded for these three runs; the failure is in the test rig, not
  the guest.
- A/B against the outgoing batch-14 build (same consumer check,
  served locally from the rollback tree with the local games mirror):
  2/2 mapped cleanly (AB1 5 frames / 70.174 s, AB2 4 frames /
  73.848 s; overlay cleared, 1,273,748 lit pixels, 0 fault lines).
  The A/B shows no fault-loop regression signal on either build —
  the fault is absent on both — and the tab crashes are statistically
  consistent with a build-independent flake: all three crashes land
  in the new-build runs, but with 3 crashes in 10 runs total the
  chance they all land in the 8 new-build runs by chance alone is
  47%. The box was under extreme memory pressure throughout (swap
  11G/11G used, 97M free; RAM 19G/23G used at the b8 crash; no
  OOM-killer event in dmesg). The tab crash is a probe-infrastructure
  flake under current box conditions, not a guest verdict, and it is
  recommended for filing as its own defect (the register's next
  number) rather than blocking this ship: the fault fix is proven by
  the 8/8 clean guest consoles and the 5 clean maps.
- Note for future lanes: the local games mirror
  (`/tmp/fd271-games-mirror.mjs`, port 8901) had died before the A/B
  runs (chromium.zip returned 000) and was restarted from its
  preserved script and verified (200, Range 206, CORS `*`) — the same
  known flake the FD-271 lane hit. The mirror was left running.

- A/B against the outgoing batch-14 build (same check, same runner,
  served from the rollback tree): FAIL, identically — 671,032 ms,
  the same "RESULT 0/ not seen within 180000ms", the same
  `WAITING KUnixSocketObject::lockCond` stack-dump shape. The
  known-good previous build fails this check the same way under the
  day's load (12–15 throughout all three runs; the 180 s window is
  far shorter than a 64-bit boot under that load — cert-x64 boots
  took 393–523 s at load 9–11). NOT a regression of the new build:
  the check is broken under current conditions. The underlying
  MSHTML/socket-wait behaviour under load is recommended for filing
  as its own defect rather than blocking this ship.
