# Merge record: FD-271 Chromium-boot fault loop — composition onto batch 15

Date: 2026-11-10. Base: integration tip `80bfd0e96` (batch 15). Lane branch:
`lane-fd271`, tip `18a3a324d`. Merge branch: `lane-merge-fd271`.

## Pool

One lane, off integ `80bfd0e96`:

- **FD-271** (lane `a8ee8f3c`, third resume; first lane `894eff8b`, second resume
  `e5df414f` — both stopped on the disk guardrail). The Chromium boot died in
  a repeated fault loop before the desktop was ready. Two mechanisms, both
  fixed:
  1. Loop (`0647f59da`): a fresh clone child's first fault was delivered on an
     alternate signal stack that was never set up, so every signal-frame write
     faulted at `0xfffffd08` and re-delivered identically until FD-205
     containment ended the process at count 129. Fix: fall back to the normal
     stack when no alternate signal stack is configured
     (`source/kernel/kthread.cpp` +11/−1). This is also the mechanism behind
     FD-115's original 2026-11-02 instance and the batch-11 a4 / batch-12
     a1/a2/b3 sightings.
  2. Trigger (`2b84f4ead`): the fresh clone child's first fetch returns null
     solely because `thread->terminating` is set by its process's `exit_group`
     racing thread creation (proven by diag-run9: exitgroup pid=77 code=1,
     then termother tid=80, then firstop term=1, then the fabricated SIGSEGV,
     the panic, and the whole guest exiting). Fix: retire a terminating thread
     silently at the three fetch-null sites (platformThread first fetch,
     `NormalCPU::run`, `CPU::runNextSingleOp`) instead of fabricating a fault.
