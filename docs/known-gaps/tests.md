### Out-of-lane gaps observed from `tools/` (NEEDS_OTHER_LANE)

- **Kernel (`source/kernel/`)**: fork/vfork/clone-without-CLONE_VM and clone3 are owned by docs/known-gaps/kernel.md on lane/winbox-p2kernel-20261023 (rechecked at tip 7f6156b43). There, fork and non-thread clone create a deep-copied child and pass wait4 tests, and vfork suspends the parent until exec or exit; the clone3 and fork/vfork rows carry the remaining work (vfork shared-memory-until-exec/exit semantics, remaining clone3 fields and flags including set_tid and cgroup). The syscall locations quoted in the previous version of this list describe this tree before that lane work and are superseded by the owning register.
- **CPU (`source/emulation/cpu/`)**: decided by the kernel lane (see the AVX row above and kernel.md): CPUID keeps AVX/AVX2/BMI clear, and an unhandled VEX opcode can no longer be skipped silently on any build; recovery is off by default everywhere and the fault delivers SIGILL through the guest signal path (testOpcodeFault64Delivery).
- **Vulkan (`source/vulkan/vk64bridge.cpp`)**: owned by docs/known-gaps/vulkan.md on lane/winbox-gb2-20261022; the asked-for log is rate-limited once per name there and the path is REJECTED-LOUDLY with VK_ERROR_FEATURE_NOT_PRESENT (see the gen_vk64pe row above). The denylist in tools/vkd3d/probe/gen_vk64pe.py is a guest-shim concern of the same lane.
- **Vulkan coverage (`tools/vkcov/METHOD.md:14-16`)**: 99 vk64 exports are stub-only, and vk32 is trap-only (303 exports). Recorded as known unimplemented surface; implementation belongs to the vk lane.
- **Vulkan work list (`tools/vkd3d/ICD_WORK_ITEMS.md:28,222,225`)**: push descriptors "not supported", flush as logged no-op, query pools listed as work items. Owned by the vk lane.
- **Runtime (`tools/rootfs64/build-wine64-zip.sh`)**: FIXED in the runtime lane (491919b04) — the build no longer ships Debian's /bin/sh dispatch script at `usr/lib/wine/wineserver`; the name is staged as a symlink to the ELF `wineserver64` and the shipped wine64.zip member was replaced with that symlink form, pinned by `check_runtime_completeness.py` (wineserver dispatch is ELF). In the shipped archive `usr/bin/wineserver` already pointed at the ELF; the script member was the sole broken entry. The runtime lane confirms the guest loader does not reach the script path in the shipped configuration (launcher sets `WINESERVER=/usr/lib/wine/wineserver64` on every spawn), so the defect was latent packaging incorrectness, not a live boot failure. This lane keeps the packaging ratchet in `packaging-prefix.test.mjs` as a guard: it tolerates only that single registered entry (which persists in the pre-merge integration archive until the runtime fix is merged and the export rebuilt) and fails on any other script entry or a missing ELF dispatch target.
- **Wine patch (`tools/buildWine/patches/wine5-lz.patch:235,297`)**: `FIXME("flags 0x%x ignored")` in `GetFileVersionInfoSizeExW` and `GetFileVersionInfoExW` (`dlls/kernelbase/version.c`). **Upstream, not dropped.** The FIXME lines are unchanged context in the patch (leading space, no `+`/`-`), so they come from the base Wine source the patch applies to (Wine 5.0 per `tools/buildWine/buildAll.sh`), not from this patch. Flag values (`tools/browser/zig/lib/libc/include/any-windows-any/winver.h:114-116`): `FILE_VER_GET_LOCALISED=0x01` is honoured, `FILE_VER_GET_NEUTRAL=0x02` and `FILE_VER_GET_PREFETCHED=0x04` are ignored and logged. Whether that changes the resource block returned was not traced in the patched code. The row is not dropped because the repo cannot show that no guest passes those bits: no Wine base tree is present to compare against, and no callers were checked. Severity: low, pending a caller check.
